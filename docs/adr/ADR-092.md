# ADR-092：项目状态变更与内容版本解耦

- 状态：Accepted
- 基线固化：2026-10-21
- 接受依据：用户 2026-10-21 指示——「我希望更改状态也不会变动版本号」；同轮反馈要求「保存修改」不再依赖单独的「保存状态」，且无改动保存不能推高版本。
- 修订关系：修订 [ADR-035](ADR-035.md) 第 2 节关于项目行版本触发器的口径、[ADR-056](ADR-056.md) 第 2 节「维护中回到进行中会递增 `row_version`」的实现口径，以及 [ADR-057](ADR-057.md) 复用该端口后的版本口径。ADR-043 的三态、进入维护中的任务门禁与三态可写，ADR-054 的任务生命周期，ADR-091 的封箱触发与副作用全部不变。
- 关联：[ADR-013](ADR-013.md) 的显式事务与锁序、[ADR-019](ADR-019.md) 的路由与幂等策略、[ADR-039](ADR-039.md) 的项目成员门禁、[ADR-073](ADR-073.md) 的搜索投影版本防旧写；新增迁移 `0057_project_status_version_semantics.sql`。
- 不在本 ADR 范围：成功提示气泡属于纯前端交互收敛，不改变接口、授权或数据语义，记录在开发日志与测试矩阵。

## 背景

1. `app.projects.row_version` 同时承担两件事：项目内容版本的乐观锁比较值，以及历史上「每次项目更新都递增」的操作计数。状态也是项目行的一列，因此每次手动切换状态或维护中自动回到进行中都会让版本加一。
2. 这带来两个用户可见问题：只改状态的「保存修改」会推进版本；没有任何内容改动也可能让版本变化。随后编辑名称或描述时，用户持有的 `If-Match` 会被一次纯状态动作无意义地作废。
3. 用户要求状态变更不再改变版本号，但项目内容编辑仍必须保留乐观锁：同一项目的内容修改不能静默覆盖另一笔较新的内容修改。
4. 原数据库触发器要求 `app.projects` 每次 UPDATE 都恰好让 `row_version + 1`。只改服务层不够，任何其他写路径仍可能通过数据库状态更新推高版本；必须在数据库约束层表达新语义。

## 决策

### 1. `row_version` 定义为内容版本

- `app.projects.row_version` 继续是项目内容版本的单调递增整数，用于 `If-Match` 与内容编辑冲突检测，不再表示项目行的所有更新时间次数。
- 只要 `status`、`updated_at`、`row_version` 之外的任一列发生变化，更新仍必须恰好让 `row_version + 1`。名称、描述、编码、粘性标记等任何内容变化都不得绕过。
- 纯状态变更允许只写 `status` 与 `updated_at`，保持 `row_version` 不变；状态不是内容编辑的一部分。

### 2. 数据库触发器是最终防线

迁移 `0057_project_status_version_semantics.sql` 替换 `app.require_project_row_version()`：

- 当 `NEW.row_version = OLD.row_version` 时，只有状态确实变化且其余业务列完全一致才放行；
- 其余任何内容变化在版本未推进时以 `check_violation` 拒绝；
- `row_version` 一旦变化，仍必须恰好为旧值 `+ 1`；
- 其他表的 `require_next_row_version` 语义不变。

触发器使用 `to_jsonb(NEW)` / `to_jsonb(OLD)` 去除 `status`、`updated_at`、`row_version` 后比较，避免遗漏未来新增列；新增项目内容列会自动落入「必须推进版本」的一侧。

### 3. 所有项目状态写入口统一

- 手动切换状态：`PostgresProjectsWritePort.updateProjectStatus` 只更新 `status` 与 `updated_at`，不写 `row_version`。
- 维护中自动回到进行中：任务创建、重新打开、恢复共用的 `reopenMaintenanceProject` 只更新 `status` 与 `updated_at`，不写 `row_version`。
- 首次任务完成：即使同时把项目从 `NOT_STARTED` 升级为 `ACTIVE`，也会写 `first_task_completed_at`，属于内容变化，因此仍恰好让 `row_version + 1`。这是「首次完成任务」与「纯状态切换」的唯一版本差异。
- 状态、审计 `project.status.change`、活动、搜索投影与封箱副作用仍在同一事务内提交；版本是否变化不影响这些副作用的可见性。

### 4. `If-Match` 与状态并发

- 写接口继续要求 `If-Match`，其值仍是当前内容版本；版本不符继续返回 409 `PROJECT_VERSION_CONFLICT`。
- 状态请求在事务内先对项目行取 `FOR UPDATE`，再重新读取状态与版本并执行三态规则；并发状态请求因此串行复核，后到请求看到前一笔的状态结果并返回 `PROJECT_STATE_CONFLICT` / `PROJECT_STATUS_LEVEL_SKIP` 等明确业务错误，而不是仅凭相同 `If-Match` 覆盖。
- 内容编辑与状态切换仍按项目行锁序串行。状态切换不推进版本，因此不会让在途的内容编辑无故变成版本冲突；内容编辑一旦成功推进版本，持有旧 `If-Match` 的后续请求仍按既有规则 409，要求刷新后重试。

### 5. 幂等、投影与响应

- `changeProjectStatus` 的响应版本语义发生变化，幂等契约版本由 `1.2.0` 升为 `1.3.0`；同一 Key、同一摘要与同契约版本的重放继续返回原 2xx，新旧契约按既有规则区分为 409。
- 搜索投影允许同 `source_row_version` 的状态刷新覆盖同一实体：状态变化不在版本上体现，但投影的 `source_status` 必须更新。旧版本仍不得覆盖新版本。
- 审计、活动摘要、通知、封箱与重放授权规则不变；不新增路由、不新增字段、不改变权限门禁。

## 被否决的方案

1. **只在服务层停止递增，保留旧触发器**：任何未来写路径或手工 SQL 只要只改状态就会被旧触发器拒绝，数据库兜底与实现不一致，否决。
2. **状态变更也递增，但前端隐藏版本号**：用户仍会在下一次编辑时遇到无意义的版本冲突，且「无改动保存不推进版本」无法成立，否决。
3. **新增独立的 `status_version` 列**：当前没有按状态版本做并发控制的需求，状态由行锁与状态规则串行化；新增列会扩大表、契约、迁移与投影维护面，否决。
4. **取消 `If-Match`**：会放宽内容并发保护，超出用户要求，也违反既有安全与数据一致性基线，否决。

## 后果

- 纯状态切换不再让项目内容版本增长；用户切换状态后继续编辑名称或描述，不会因为状态动作本身而得到 409。
- 内容修改仍需显式处理 `PROJECT_VERSION_CONFLICT`；这是有意的乐观锁行为。
- 审计、活动与搜索投影会出现「同一项目版本下多次状态变化」，读取方不得假设一个版本只对应一次状态事件；业务状态与事件时间仍是唯一真相。
- 维护中自动回到进行中与非维护中的重复触发保持无操作，不会造成版本空转。
- 数据库层仍拒绝所有未推进版本的内容更新，避免绕过服务层破坏并发保护。

## 部署与回滚

- 部署顺序：先应用迁移 `0057`，再部署新 API。旧 API 在状态切换时仍会递增版本，与新触发器兼容；新 API 在旧触发器下则会因状态更新不递增版本而失败，因此不能先部署新 API。
- 回滚顺序：先回退 API 到仍会递增版本的应用版本，再恢复旧触发器函数。只恢复旧触发器而保留新 API 会让状态切换失败；反向只回退 API 而保留新函数则仍可运行，因为旧 API 的 `+1` 仍满足新触发器。
- 迁移不重写历史版本，不回溯修正审计或搜索投影；回滚也不需要数据订正。
