# ADR-093 企业微信项目群通知收敛为项目动态单一来源

- 状态：Accepted
- 决策日期：2026-10-21
- 接受依据：用户要求整理项目群通知，消除同一次任务派发的重复消息、把普通任务编辑误归为“任务派发”，并让群通知不受个人通知开关影响。
- 关联：修订 [ADR-090](ADR-090.md) 的桥接来源与分类口径；沿用 [ADR-077](ADR-077.md) 的项目群投递队列、[ADR-014](ADR-014.md) 的 MEMBER 可见动态投影与 [ADR-040](ADR-040.md) 的负责人集合语义；无新增路由、无迁移、无依赖变化。

## 1. 背景

ADR-090 让桥接在物化 `app.wecom_group_deliveries` 前读取项目级五类开关，但群投递仍同时读取两路来源：

1. `app.notifications` 中的 `task.assigned`；
2. `app.activity_projection` 中 `visibility_scope = 'MEMBER'` 的项目动态。

两路来源会带来三个用户可见问题：

- 同一次任务创建或新增负责人会同时写个人通知和任务动态，桥接各物化一行，群里收到两条含义相同的消息；
- `task.update` 不区分“改标题、描述、优先级”和“负责人实际变化”，现有映射把全部更新都归为 `task.assign`，与 UI 文案“新任务、负责人变更”不一致；
- `task.assigned` 个人通知会按个人通知偏好过滤；当负责人关闭个人任务提醒时，项目群也会静默收不到任务派发，两个独立开关发生耦合。

## 2. 决策

### 2.1 群消息只以项目动态为规范来源

`bridge.mjs` 只物化 `app.activity_projection` 中 `visibility_scope = 'MEMBER'` 的动态，不再从 `app.notifications` 生成新的群投递行。

这样：

- 一次业务动态只产生一行 `ACTIVITY` 投递，跨来源重复从结构上消失；
- 项目群开关不再受任何成员的个人 `task.assigned` 偏好或收件人集合影响；
- 个人单聊/站内通知链路和项目群链路继续彼此独立。

升级前已经写入 `app.wecom_group_deliveries` 且状态为 `PENDING` 的旧 `NOTIFICATION` 行仍由 `long-conn.mjs` 兼容消费，避免升级丢失已排队消息；桥接不会新增此类行。

### 2.2 精确区分任务创建与普通编辑

`notification-categories.mjs` 使用 `groupActivityDisposition(activityType, metadata)` 返回 `{ category, skip }`：

- `task.create` → `task.assign`；
- `task.update` 且 `metadata.assignmentChanged === true` → `task.assign`；
- `task.update` 缺失该标记或为 `false` → `skip = true`，不进入群发送队列；
- 其余已知任务状态、记录、项目成员和删除事件按 ADR-090 的五类映射；
- 未识别动态仍默认放行，但不再按 `sourceEntityType` 猜测类别，避免未来未知的 `TASK` 动态被误归到 `task.assign`。

旧数据中的 `task.update` 没有 `assignmentChanged` 时按“未确认改派”跳过；新写入的任务动态必须携带该字段。

### 2.3 任务动态携带改派元数据

任务创建/更新写入 `activity_projection.metadata` 时补充：

- `assignmentChanged`：本次负责人集合是否实际变化；
- `assigneeIds`：写入后的负责人 ID 集合；
- `previousAssigneeIds`：写入前的负责人 ID 集合。

这些字段只用于投影消费和审计展示，不替代 `task_assignees` 作为负责人真相。真实改派时动态摘要使用“任务改派”，普通编辑仍为“任务更新”。

### 2.4 生效边界

- 项目级五类开关、缺行全开、关闭不回溯、已排队/已发送不回溯的语义保持不变；
- 群开关只影响此后物化的 MEMBER 动态；
- 群通知不读取、不改写任何个人通知偏好；
- `groupNotificationTypes` 与 `startFromGroupNotificationId` 不再参与群投递；旧状态文件中的 `lastGroupNotificationId` 被忽略，`lastActivityId` 继续作为唯一群动态游标。

### 2.5 项目群消息展示

群动态使用与个人通知一致的 `text_notice` 模板卡片。`group-message.mjs` 作为纯展示层，输出统一来源、主标题、编号、项目副标题和最多 6 行关键字段，卡片跳转地址由 `long-conn.mjs` 的 `cardActionUrl` 提供：

- 任务展示负责人、优先级 / 状态、截止时间、功能或模块；
- 模块和功能展示各自编码与所属模块；
- 项目状态、成员、迭代记录和 GitHub 动态使用事件语义标题，不直接复述扁平摘要；
- 未识别事件仍可渲染，并从摘要提取可读对象，不输出 `null` 或 `undefined`；
- 2026-10-21 已在真实项目群验证 `aibot_send_msg` + `chat_type:2` 接受 `template_card`，返回 `errcode=0`。

项目封箱仍使用原有“Markdown 文案 + 海报”，其他项目动态使用模板卡片。展示层不改变 ADR-090 的五类开关、ADR-093 的单一来源和去重口径，也不改变发送限速、绑定或重试行为。

## 3. 非目标

- 不改变 `app.notifications` 表、个人通知偏好、单聊投递或站内通知读取；
- 不改变群绑定、码兑换、握手或发送限速；
- 不新增数据库列或迁移；
- 不回溯修复历史重复消息，也不删除已排队或已发送记录；
- 不为未知动态提供新的开关类别。

## 4. 后果与验收

- 同一次任务创建/改派只产生一条群消息；
- 普通任务编辑不再触发“任务派发”群消息；
- 关闭所有负责人个人任务提醒后，项目群任务派发仍按项目开关正常产生；
- 分类单元测试覆盖创建、真实改派、普通编辑跳过、四类已知事件、未知动态默认放行、缺行全开与显式关闭；
- 展示层单元测试覆盖任务上下文、改派、模块 / 功能、项目状态与未知事件的降级输出；
- API 集成测试验证 `task.create` / 两次 `task.update` 的 `assignmentChanged`、当前负责人和原负责人元数据。
