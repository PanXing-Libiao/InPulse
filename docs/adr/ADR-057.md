# ADR-057：任务重新变为未收尾即让维护中项目回到进行中

- 状态：Accepted
- 基线固化：2026-10-08
- 接受依据：用户 2026-10-08 指示——「现在问题我重新打开任务，将任务变为进行中还是处于维护中」（承接同日 [ADR-056](ADR-056.md) 的「维护中项目新建任务即回到进行中」）。
- 修订关系：**扩展 [ADR-056](ADR-056.md) 的触发面**（由「任务创建」扩为「任务重新变为未收尾」，新增 `TASK_REOPENED` 与 `TASK_RESTORED` 两个 `trigger` 取值），并**修订 ADR-056 第 5 节非目标第 2 条**（该条把「推进任务状态」整体排除在外，现收窄为「只有让任务重新变为未收尾的状态流转才触发」）。ADR-035 的「首次任务完成自动升级」、ADR-043 的三态与门禁、ADR-056 的其余决策（同事务副作用、不发通知、不动 `first_task_completed_at`）全部不变。
- 关联：[ADR-054](ADR-054.md)（任务状态机只有 `TODO | DONE | CANCELED` 与 `COMPLETE` / `REOPEN` / `CANCEL` / `RESTORE` 四类流转）、[ADR-043](ADR-043.md) §6（三态都可写）。
- 版本口径修订：[ADR-092](ADR-092.md) 起重新打开与恢复触发的维护中回到进行中只改状态与 `updated_at`，保持 `row_version`；下方 2026-10-08 的测试证据保留为历史记录，当前测试口径见 ADR-092。

## 背景

1. ADR-056 确立的口径是「**任务创建**代表项目重新开工」：维护中项目一旦有新任务，就在同一事务内回到进行中。但它按 §5 非目标第 2 条刻意排除了状态流转，只覆盖创建。
2. 状态流转里有另一组同样代表「重新开工」的动作：`REOPEN`（`DONE → TODO`）与 `RESTORE`（`CANCELED → TODO`）——两者都让一个**已经收尾**的任务变回未收尾，项目因此重新出现待办，与「维护中 = 主体已完成、只做小修小补」冲突；其中「把刚做完的任务重新打开」是最常见的形态（做完发现没做完，需要继续跟进）。
3. 现有行为的不一致（用户实测路径）：项目切「维护中」→ 在同一任务上点「重新打开」→ 任务回到未完成，项目仍显示「维护中」；而紧接着新建一个任务则项目会回到「进行中」。同一类事实、两个动作，得到不同结果。
4. 反向同样不成立：`COMPLETE`（`TODO → DONE`）与 `CANCEL`（`TODO → CANCELED`）让项目**减少**未收尾任务，不是重新开工，不触发（`COMPLETE` 的「首次完成」升级仍只由 ADR-035 管）。

## 决策

### 1. 触发条件与范围

- 触发条件：命令执行前项目 `status = 'MAINTENANCE'`，且命令执行后任务的 `work_status` 由收尾态变为未收尾态。当前状态机下恰好是两个动作：`REOPEN`（`DONE → TODO`）与 `RESTORE`（`CANCELED → TODO`）。
- 统一直觉：**凡是让项目重新出现未收尾任务的命令都触发**（创建 + 重新打开 + 恢复），因此端口方法取中性名 `reopenMaintenanceProject`，由调用方传入 `trigger`。
- 覆盖入口：`transitionTask`（功能级）与 `transitionModuleTask`（模块级）走的是同一个 `TasksManagementService.transition()`，因此两个真实 HTTP 路由全部生效。
- 不触发：`COMPLETE`、`CANCEL`（减少未收尾任务）、编辑任务、合并 / 解除合并、记录发布（不改变任务工作状态），以及项目已是 `NOT_STARTED` / `ACTIVE` 时的任何命令（不写审计、不改版本、不推高 `row_version`）。

### 2. 与 ADR-056 共用同一条副作用链

- 端口：`ProjectsWritePort.reopenMaintenanceProject(tx, { projectId })`——**由 ADR-056 的 `reopenMaintenanceProjectOnTaskCreate` 更名而来**，实现与返回记录 `ProjectMaintenanceReopenRecord` 完全不变（单条条件 UPDATE，`WHERE p.status = 'MAINTENANCE' AND p.deleted_at IS NULL`，未命中返回 `undefined`）。**2026-10-09 修订（[ADR-062](ADR-062.md)）**：`app.projects.deleted_at` 列已由迁移 `0038` 删除，实现中的 `p.deleted_at IS NULL` 条件随之移除，谓词现为 `WHERE p.id = $1 AND p.status = 'MAINTENANCE'`，命中语义不变。
- 私有方法：`TasksManagementService.reopenMaintenanceProject(tx, input, result, trigger)` 新增 `trigger` 形参，`trigger: "TASK_CREATED" | "TASK_REOPENED" | "TASK_RESTORED"`；两处调用方分别为 `execute()` 创建分支（`TASK_CREATED`）与 `transition()` 的 `REOPEN` / `RESTORE` 分支（`TASK_REOPENED` / `TASK_RESTORED`）。
- 副作用逐项与 ADR-056 相同：
  - 审计 `project.status.change`，`eventPayload` 含 `automatic: true`、`trigger`、`taskId`、`before: { status: "MAINTENANCE" }`、`after: { status: "ACTIVE" }`；
  - 活动投影 `PROJECT_STATUS_CHANGED`（摘要「项目重新开工：{name} 由维护中回到进行中」，`metadata` 含 `trigger` 与 `taskId`，`sourceStatus` / `sourceRowVersion` 取切换后的项目行）；
  - 搜索投影 `PROJECT` 实体按切换后的状态与行版本刷新；
  - **不写**通知（沿用 ADR-035 / ADR-056 的收窄口径）；**不写** `first_task_completed_at`（粘性标记的唯一来源仍是任务完成）。
- 触发点位于 `transition()` 的通知块之后、返回之前：任务级通知（如重新打开的 `task.reopen`）照旧发送，与项目级通知的缺席互不干扰。

### 3. 并发与锁序

- 与 ADR-056 §3 完全一致：条件 UPDATE 只命中维护中的行，非维护中不取行锁、不推高 `row_version`；`transition()` 此前已通过 `checkProjectForWrite` 对项目行持有 `FOR SHARE`，同一事务内的写锁升级不跨事务、不引入新的等待环，也不改变 AGENTS.md §6 的父级到子级取锁顺序。
- 同一任务不可能在同一事务内既完成又重新打开，因此「创建 + 重新打开」的组合触发不会在同一事务里写两条状态审计。

### 4. 契约与接口面

- **不新增路由、不改任何 Schema 字段、不改幂等摘要输入与重放策略**：`transitionTask` / `transitionModuleTask` 的 `idempotencyContractVersion` 保持既有版本（响应 `TaskItem` 的字段与类型未变，状态切换是既有命令的副作用）。幂等重放按既有记录返回原响应，**不会**重复执行状态切换。
- 契约注释同步：`packages/api-contract/src/contracts/projects.zod.ts` 的 `ProjectStatus` 说明由「新建任务」扩为「任务重新变为未收尾（新建、重新打开或恢复）」。JSDoc 不进产物，`contract:generate` 无漂移。
- 前端必须同步失效项目缓存：`apps/web/src/features/tasks/TaskStatusPanel.tsx` 的 `onSuccess` 失效键在既有列表之外补 `"projects"`（项目卡片与项目详情分别读 `["projects"]` 与 `["projects", "detail", projectId]`）。只补服务端而不失效缓存，会让「任务已回到未完成、项目卡片仍显示维护中」这个 bug 以另一个形态复现。

### 5. 非目标

1. **不**改「未开始 → 进行中」的触发条件与通知口径（ADR-035 原样有效）。
2. **不**在编辑任务、合并 / 解除合并、发布记录时切换项目状态，也**不**让 `COMPLETE` / `CANCEL` 触发。
3. **不**做反向自动：项目状态变化不影响任何任务的 `work_status` / `lifecycle_status`。
4. **不**发站内通知（沿用 ADR-035 / ADR-056 的收窄口径）。
5. **不**回溯历史数据：存量「维护中但存在未收尾任务」的项目保持原状。
6. **不**放宽「进入维护中要求任务全部收尾」（ADR-043 §4，409 `PROJECT_MAINTENANCE_TASKS_OPEN`）。

## 影响与验证

- **数据库**：无迁移、无新表 / 新列 / 新角色；只使用 `app.projects.status` / `row_version` / `updated_at` 既有列。
- **契约**：无改动。Route Registry 仍为 101 条，OpenAPI 与生成客户端无漂移（`contract:drift` 5 产物）。
- **后端**：`projects/projects-write.port.ts`（方法更名 + JSDoc 扩写触发面）、`projects/postgres-projects-write-port.ts`（方法更名，SQL 不变）、`tasks/tasks-management.service.ts`（私有方法增 `trigger` 形参、`execute()` 传 `TASK_CREATED`、`transition()` 新增 `REOPEN` / `RESTORE` 分支）。
- **测试证据**（本地 2026-10-08，真实 PostgreSQL 18.6 + PGroonga 于 `app_ci`）：`apps/api/test/task-create-maintenance-reopen.integration.test.ts` 由 5 例扩为 **9 例**，新增四例：
  1. 维护中项目重新打开已完成任务后 `status='ACTIVE'`、`row_version` 递增、`first_task_completed_at` 仍为 `NULL`，审计恰一条且 `trigger: "TASK_REOPENED"`，活动与搜索投影 `sourceRowVersion` 一致，**无** `project.status.change` 通知；同时断言前置的 `COMPLETE` 未改变项目状态；
  2. 维护中项目恢复已取消任务后同理，审计 `trigger: "TASK_RESTORED"`；同时断言前置的 `CANCEL` 未触发；
  3. 进行中项目重新打开任务不写任何项目状态变更副作用（状态与 `row_version` 不变、无审计与活动）；
  4. 重新打开与状态切换在同一事务：外层抛错后项目仍为 `MAINTENANCE`、任务仍为 `DONE`、无审计与活动、无 `task.reopen` 通知。
- **鉴别性验证**：临时停用 `transition()` 中的触发调用后，新增用例 1、2 转红（`expected 'MAINTENANCE' to be 'ACTIVE'`），其余 7 例保持绿；恢复实现后 9 例全绿。说明新用例真的在测触发点，而不是被既有副作用顺带通过。
- **未覆盖 / 已知偏差**：并发「一个事务重新打开、另一个事务新建」的组合未写真库竞态用例（锁语义与 ADR-056 §3 同源）；`pnpm test:e2e` 与 GitHub Actions 不在本批执行范围。

## 后果

- 修正了 ADR-056 留下的动作间不一致：创建、重新打开、恢复这三个「让项目重新开工」的动作现在结果一致，项目状态与事实不会因为「用了哪个按钮」而分叉。
- 连带效果：维护中的项目不产出任务中心卡片（2026-09-30 口径），重新打开任务后项目回到进行中，该任务重新出现在任务中心与任务看板，属预期结果。
- 代价：项目状态切换的隐式副作用面比 ADR-056 更宽（三个动作都能触发），因此审计与活动里的 `trigger` 取值必须保持区分度（`TASK_CREATED` / `TASK_REOPENED` / `TASK_RESTORED`），「谁在什么时候、因为什么让项目回到进行中」仍可追溯。
- 若将来再扩展触发面（例如合并 / 解除合并也算），必须新增 ADR 修订，并把实现位置（`TasksManagementService.execute()` / `transition()`）、审计 `trigger` 取值与本节同步。
