# ADR-090 企业微信项目群通知策略由服务端持久化并在桥接物化前过滤

- 状态：Accepted；群消息来源与 `task.update` 分类口径由 [ADR-093](ADR-093.md) 修订（2026-10-21），数据模型、API、权限与幂等决策继续有效。
- 决策日期：2026-10-20
- 接受依据：用户反馈项目成员页的「通知选项」只改了浏览器状态，企业微信机器人仍按旧口径发送群消息，要求群消息通知策略与实际机器人投递对齐。
- 关联：扩展 [ADR-077](ADR-077.md) 的项目群投递；沿用 [ADR-013](ADR-013.md)（显式事务）、[ADR-019](ADR-019.md)（数据库级幂等）、[ADR-039](ADR-039.md)（组长例外门禁）与 [ADR-029](ADR-029.md)（统一错误体）；新增迁移 `0055_project_wecom_group_notification_options.sql`；新增 1 条路由（128 → 129）。

## 1. 背景

ADR-077 第二批已经能把任务派发通知和 MEMBER 可见项目动态物化到 `app.wecom_group_deliveries`，再由长连接桥接按项目绑定的 `chatid` 发送到企业微信群。但前端「通知选项」弹窗最初只把五类开关写入 `localStorage`；桥接进程没有读取这份浏览器本地状态，因此用户关闭某一类后，群机器人仍会继续推送。

项目群通知策略是项目级配置：同一项目绑定一个群，群内成员应看到同一套开关，不能依赖某个组长的浏览器。并且桥接是独立进程，不能读取用户浏览器存储。策略必须落到数据库，并由桥接在生成群投递队列前按同一份数据过滤。

## 2. 决策

### 2.1 服务端数据模型

迁移 `0055` 新增 `app.project_wecom_group_notification_options`：

- 每个项目至多一行，`project_id` 为主键并外键引用 `app.projects(id)`，项目删除时级联清理。
- 五个布尔列分别对应五类群消息：`task_assign_enabled`、`task_status_enabled`、`record_enabled`、`project_member_enabled`、`scope_delete_enabled`，默认全部为 `TRUE`。
- 没有行等价于五类全部开启；首次保存才插入。`row_version` 从 1 开始，每次覆盖保存递增。
- `app_runtime` 只有 `SELECT / INSERT / UPDATE`；`app_backup` 只读；迁移内包含表归属、级联外键与授权断言。

### 2.2 契约与权限

- `GET /api/v1/projects/{projectId}/wecom-group` 的响应新增 `notificationOptions.disabledCategories`；缺行返回空数组。原有绑定三态、投递错误和机器人链接字段保持不变。
- 新增 `PUT /api/v1/projects/{projectId}/wecom-group/notification-options`（`updateProjectWecomGroupNotificationOptions`），整组替换 `disabledCategories`。
- 读取由项目活跃成员或系统管理员执行，非成员按资源不存在 404；写入仅限系统管理员或本项目组长，普通成员 403 `PROJECT_WECOM_GROUP_FORBIDDEN`。
- 写入要求同步 CSRF 与 `Idempotency-Key`，数据库级幂等契约 1.0.0；项目必须存在 ACTIVE 群绑定，否则 409 `PROJECT_WECOM_GROUP_NOT_BOUND`。
- 幂等重放重新校验当前认证、组长或管理员身份，并确认项目仍绑定 ACTIVE 群；解绑或换绑后不得重放旧的保存成功响应。
- 保存写审计 `project.wecomGroup.notificationOptions.update`，记录 `groupBindingId`、`before` 与 `after`；审计和配置写入使用同一事务。

### 2.3 桥接过滤

`bridge.mjs` 每轮物化群投递前读取项目开关，缺行按全开处理，然后对通知和项目动态做确定性分类：

- `task.assign`：`task.assigned` 通知，以及 `task.create` / `task.update` 动态。
- `task.status`：任务完成、重新打开、取消、恢复、合并、解除合并的通知与动态。
- `record`：迭代记录发布、修订、追加遗留问题、恢复，以及遗留问题转任务；作废动态按既有可见性规则为 `ADMIN_ONLY`，不进入群推送。
- `project.member`：项目创建、状态变化、成员加入 / 移出 / 角色调整、模块与功能信息更新、外部链接变化。
- `scope.delete`：模块、功能、任务删除。
- 未识别的未来通知或动态默认放行，避免新事件因漏登记映射而静默丢失。
- 关闭类别不再写入新的 `PENDING` 投递行；来源游标照常前进。重新开启不会补发关闭期间的历史，已排队和已发送消息也不回溯。

桥接只做固定映射和布尔判断，不执行用户输入拼接 SQL，也不改变个人单聊投递链路。

### 2.4 前端交互

- 弹窗继续在切换后立即保存，但改为调用服务端 PUT；保存期间禁用全部开关，失败回滚视图并显示统一错误文案。
- 服务端响应直接更新 React Query 缓存，避免重新拉取时覆盖快速连续操作；成功提示不会因缓存刷新被立即清空。
- 服务端保存成功后，继续把同一份关闭列表同步到当前浏览器的站内通知筛选，保留既有行为；其他成员的站内通知仍由各自的个人通知设置管理。
- 文案明确说明：群开关只影响之后产生并进入群发送队列的消息，历史、已排队和已发送消息不回溯。

## 3. 非目标

- 不改变个人单聊推送、个人通知偏好或站内通知历史。
- 不按成员设置群消息偏好；群开关是项目级共享配置。
- 不编辑、撤回或重发已排队的 `wecom_group_deliveries` 行。
- 不新增群内命令，不允许普通成员修改开关。
- 不把浏览器 `localStorage` 作为群投递的真相来源。

## 4. 后果与验收

- 项目群通知开关从单浏览器状态升级为可审计、可重放、跨设备一致的项目配置。
- 桥接新增独立分类模块 `notification-categories.mjs`；未知事件默认放行的兼容策略写入桥接 README。
- 路由总数 128 → 129，`permissions:check` 与 `contract:validate` 均按 129 条校验。
- 定向验收覆盖：默认全开、成员只读、组长与管理员保存、CSRF、非法类别 422、审计前后值、同 Key 重放不重复写、不同 body 409、解绑后保存与重放均 409；前端覆盖切换即保存、失败回滚、成功提示与站内筛选同步。
