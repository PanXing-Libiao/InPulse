# ADR-105 企业微信 Webhook 项目群通知通道

- 状态：Accepted
- 日期：2026-10-28
- 决策人：项目负责人（用户指示）
- 关联：扩展 [ADR-077](ADR-077.md) 的项目群目标模型、[ADR-090](ADR-090.md) 的项目级通知开关与 [ADR-093](ADR-093.md) 的群动态单一来源；沿用 [ADR-013](ADR-013.md) 的显式事务、[ADR-019](ADR-019.md) 的数据库级幂等、[ADR-070](ADR-070.md) 的加密 keyring 与 [ADR-104](ADR-104.md) 的 projectWecomGroup 能力门禁；新增迁移 `0063_project_wecom_webhooks.sql` 与两条路由（133 → 135）

## 1. 背景

现有项目群通知依赖企业微信“智能机器人（API 模式 + 长连接）”：项目签发一次性绑定码，群内先有人 @机器人 激活，再由桥接通过 `aibot_send_msg` 和 `chat_type:2` 投递。该通道受单机器人单长连接、先对话激活与机器人侧限速约束。

用户要求同时支持项目绑定企业微信群 Webhook：项目内变动或任务派发时向对应项目群推送，并允许一个项目配置多个 Webhook。Webhook 与现有个人单聊、智能机器人群通知并存。

## 2. 决策

### 2.1 统一目标表与通道类型

泛化 `app.project_wecom_groups` 为“项目群通知目标”，新增：

- `channel_type`：`BOT` 或 `WEBHOOK`，历史行在迁移后固定为 `BOT`；
- `webhook_label`、`webhook_url_ciphertext`、`webhook_url_key_version`、`webhook_url_fingerprint` 与 `webhook_url_hint`；
- `wecom_chat_id` 对 `WEBHOOK` 为 `NULL`，对 `BOT` 仍必填。

约束保持“一个项目至多一个 ACTIVE 智能机器人目标、一个群至多对应一个 ACTIVE 智能机器人目标”；Webhook 允许一个项目多个 ACTIVE 目标，但同一个规范化 Webhook URL 全局至多绑定一个 ACTIVE 目标。项目可同时拥有一个智能机器人目标和多个 Webhook 目标，因此同一群若同时被两种方式覆盖会收到重复消息，界面必须明确提示。

目标解绑仍是 `ACTIVE → REVOKED` 状态流转，不物理删除；既有投递历史按目标行保留。项目物理删除的清理边界不变。

### 2.2 Webhook 目标 API

`GET /projects/{projectId}/wecom-group` 保持现有字段，并新增 `webhookTargets` 列表。`state` 在智能机器人或至少一个 Webhook 目标为 ACTIVE 时为 `BOUND`；顶部 `boundAt` / `boundByName` 仍表示智能机器人目标，Webhook 各自返回自己的绑定时间、绑定人和最近投递错误。响应不返回完整 URL。

新增：

- `POST /projects/{projectId}/wecom-group/webhooks`（`createProjectWecomWebhook`）：请求 `{ label, webhookUrl }`，返回脱敏后的 Webhook 目标；
- `DELETE /projects/{projectId}/wecom-group/webhooks/{bindingId}`（`deleteProjectWecomWebhook`）：解除指定 Webhook 目标。

两条路由均要求当前 Session、同源、CSRF、数据库级幂等与 `projectWecomGroup` 能力门禁；普通实现沿用“无权成员 403、非成员 404”的统一语义。审计动作分别为 `project.wecomGroup.webhook.create` 与 `project.wecomGroup.webhook.delete`，只记录目标 id、标签、URL 尾号和状态，不记录完整 URL、Webhook Key 或密文。

原 `DELETE /projects/{projectId}/wecom-group` 只解除 ACTIVE 智能机器人目标，不再影响 Webhook。管理员更换机器人时调用的 `app.revoke_wecom_bindings_on_robot_change()` 同样只撤销 `BOT` 目标与个人绑定，Webhook 保持可用。

### 2.3 URL 保管与校验

Webhook URL 含可直接发消息的 Key，按 Secret 处理：

1. 只接受规范形式 `https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=...`；拒绝其他域名、用户信息、片段、额外查询参数和非法 Key；
2. 使用现有 `WECOM_ROBOT_ENCRYPTION_KEY_FILE` AES-256-GCM keyring，但 AAD 独立为 `app.project_wecom_groups.webhook_url`；
3. 数据库只保存密文、主密钥版本、SHA-256 URL 指纹与尾 4 位提示；API、日志、审计与错误体不得返回完整 URL；
4. 同一 ACTIVE 目标的 URL 指纹唯一，重复绑定返回 409；单项目 ACTIVE Webhook 上限为 20，防止误配置无限扇出；
5. 修改或删除目标不会改写历史投递记录。

### 2.4 投递与限速

`bridge.mjs` 继续只物化 MEMBER 可见项目动态；`insertGroupDelivery` 为项目当前全部 ACTIVE 目标各写一行，因此天然支持一个项目扇出到多个 Webhook。`long-conn.mjs` 按 `channel_type` 选择发送器：

- `BOT`：保持现有 `aibot_send_msg`、`chat_type:2`、30 条/分钟与 1000 条/小时；
- `WEBHOOK`：向解密后的 URL POST 现有 `markdown` / `template_card` / `image` 消息体，Webhook 成功响应必须为 `errcode = 0`；图片 base64 解码后不得超过 2 MB；
- 每个 Webhook 目标独立限速 20 条/分钟；达到窗口时该投递行保持 PENDING，并跳过该目标处理其后的其他目标，不能阻塞其他 Webhook；
- Webhook 发送不依赖智能机器人长连接是否订阅。未订阅时仍消费 Webhook 行；BOT 行保持待命；
- 429、网络超时、`errcode = 45009` 与明确限频文案按可重试处理；其他 4xx / `errcode` 非 0 标记 FAILED 并回写目标的 `last_delivery_error`。

Webhook 与智能机器人继续共用项目级五类通知开关；不为单个 Webhook 再拆开关。关闭开关只影响之后物化的消息，不回溯历史。

### 2.5 部署与非目标

`deploy/test-vm` 与 `deploy/prod` 的 `wecom-bridge/app` 必须保持同一实现。迁移新增 `0063`，不修改任何历史迁移。

非目标：

- 不通过企业微信 API 自动创建群或自动获取群 Webhook；群与 Webhook 仍由用户在企业微信后台创建；
- 不把 Webhook 当自建应用，不新增 access_token、通讯录或群管理权限；
- 不改变个人单聊、站内通知或个人通知偏好；
- 不新增按 Webhook 的通知类别开关，不重放历史消息。

## 3. 后果与验收

- 用户可在同一项目配置多个 Webhook，也可与智能机器人并存；界面明确提示重复投递风险；
- Webhook URL 不进入 API 响应、审计、日志或错误文本；
- 更换智能机器人只撤销 BOT 绑定，Webhook 保持 ACTIVE；
- 未建立长连接时，Webhook 仍可正常消费；
- 真实 PostgreSQL + HTTP 集成覆盖权限、加密、去重、多目标、删除隔离、通知选项、机器人更换隔离与审计；
- 桥接单元测试覆盖消息体、2 MB 限制、目标级限速、成功 / 限流 / 非零 errcode / 超时错误分类；
- 静态门禁覆盖 `contract:validate` 135 条路由、`contract:drift`、`permissions:check`、类型检查、迁移检查与文档检查。
