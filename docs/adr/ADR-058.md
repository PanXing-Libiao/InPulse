# ADR-058：取消任务改为「二次确认后删除任务」——软删除、作废记录、解除链接，不提供恢复入口

> **部分条款已被 ADR-096 替代（2026-10-23）**：任务删除已从软删除改为物理删除，任务本体、状态历史、负责人、聚合组关系、链接关联与全部迭代记录/版本/遗留项会被永久清除；只保留审计、项目动态与 `task.delete`。仍有效的契约字段、聚合组关闭后剩余成员转 `DETACHED`、以及项目成员不因删除而获得记录作废特权等口径继续沿用。

- 状态：Accepted
- 基线固化：2026-10-09
- 接受依据：用户 2026-10-09 指示——「现在我需要更改取消任务，取消任务以后要变成先二次确认，确认后彻底删除这个任务，然后那些任务的github链接要取消关联，如果这个任务有迭代记录要作废，可以点击取消任务以后你刷新页面前还能点击恢复任务，但是刷新后就不行，而且就算取消任务，项目动态和审计日志里面也需要有保留取消任务的记录」。经四轮澄清后收敛为：**不要恢复入口**（「A：不要了，取消即删除」）、**不做完整还原**（「不做这个了」）、**记录自动作废**（「A：自动作废（推荐）」）、**合并组自动解除**（「A：自动解除后删除（推荐）」）。
- 修订关系：**修订 [ADR-054](ADR-054.md) 的「取消」语义**——ADR-054 下线任务归档时保留的 `CANCEL` 流转从此不再由前端提供入口，任务层新增「删除」命令；**扩展 [ADR-049](ADR-049.md) 的软删除范式**到任务（同样的「保留全部历史 + 退出可见范围」形态，但不提供 ADR-051 那样的还原与彻底删除）；ADR-024 的记录作废不变量、ADR-022 的链接类型化关联、ADR-037 §3 看板口径、ADR-050 的可见性口径全部不变。

## 背景

1. 任务层此前的收尾动作是「取消任务」（`work_status: TODO → CANCELED`）与「重新打开」（`CANCELED → TODO`）。用户的实际诉求是「取消 = 这个任务不要了」，而旧实现把取消做成一个**可逆的状态**：任务仍留在任务中心（`includeCanceled` 可勾选显示）、仍占用编号、仍参与搜索投影、其迭代记录与 GitHub 链接原样保留。
2. 用户明确要的是更彻底的语义：二次确认 → 删除 → 链接解除关联 → 迭代记录作废 → 项目动态与审计日志保留记录。
3. 用户在需求里同时提到「刷新页面前还能点击恢复任务，但是刷新后就不行」。这条**按字面无法与「彻底删除」并存**——恢复需要任务行仍然存在，而「彻底删除」要求它不存在；「刷新前可恢复」只是把恢复做成一个内存态，实现上等价于**前端确认弹窗的撤销窗口**，对服务端没有任何意义（刷新后无论如何都恢复不了，说明它不是一条业务能力）。
4. 经澄清，用户放弃恢复入口（「不要了，取消即删除」），也不要求把已解除的链接重新挂回、把已作废的记录恢复（「不做这个了」）。冲突面因此只剩一个：**物理删除 vs 软删除**。

## 决策

### 1. 物理删除不可行，采用软删除

- `app.tasks` 被 **7 张表**以 `ON DELETE RESTRICT` 外键引用：`change_records`、`task_status_history`、`task_external_links`、`task_group_members`、`task_feature_impacts`、`task_assignees`、`leftover_task_links`。物理删除必须先级联或解除这 7 类引用，而其中 `task_status_history` 与 `change_records` 是**必须保留的业务历史**（AGENTS.md 第 6 节：业务历史默认通过归档、作废或新版本保留，不物理覆盖或删除）。
- 审计链只追加（[ADR-008](ADR-008.md)）：删除任务会留下 `task.delete` 审计行，该行的 `target_id` 指向已被删除的任务 ID；若同时物理删除任务行，审计记录将指向不存在的对象，且 `change_records.task_id` 的复合外键（`change_records_task_project_fk`）会阻塞删除。项目层之所以能物理删除（[ADR-051](ADR-051.md)），是因为它走 `app.purge_project` 专用窄口把**整条项目链**一起删掉；任务层没有等价的「整条任务链」边界（记录、历史、聚合组关系属于不同聚合）。
- 因此任务删除与项目删除同范式：`app.tasks` 新增 `deleted_at` / `deleted_by` 两列，**删除 = 标记 + 退出全部可见与可写范围**，业务历史（编号、描述、状态历史、审计、动态、迭代记录）原样保留。与 ADR-049 的差别只有一条：**任务不提供还原与彻底删除**（用户已明确不要恢复入口），物理删除只随其所属项目的删除一并发生。**2026-10-09 修订（[ADR-062](ADR-062.md)）**：项目层已改为物理删除（原 ADR-051 的「彻底删除」现为唯一删除形态），而 ADR-055 的「保留期自动清理」已整体下线；本节其余内容不变。

### 2. 命令与契约

- 两条新写路由，与既有的任务路径同构（模块级任务无功能段）：

  | operationId | method + path | 成功响应 |
  | --- | --- | --- |
  | `deleteTask` | `POST /api/v1/projects/{projectId}/modules/{moduleId}/features/{featureId}/tasks/{taskId}/delete` | 200 `TaskDeletionResponse` |
  | `deleteModuleTask` | `POST /api/v1/projects/{projectId}/modules/{moduleId}/tasks/{taskId}/delete` | 200 `TaskDeletionResponse` |

- 请求体 `DeleteTaskRequest { reason: string | null }`（1～10000 字符，可空，空白回落 `"任务已被删除"`）；响应 `TaskDeletionResponse` 给出 `id` / `projectId` / `moduleId` / `featureId` / `code` / `title` / `workStatus` / `deletedAt` / `deletedBy` / `voidedRecordCount` / `removedLinkCount` / `detachedGroupRole`。
- 策略：`session` + CSRF + 数据库级幂等（`idempotencyContractVersion: 1.0.0`）+ `If-Match` 版本门禁；`auditAction: "task.delete"`；`lockOrder: ["project","module","feature","task","taskGroup"]`（AGENTS.md 第 6 节的父级到子级顺序 + 任务 ID 升序）。
- Route Registry 由 101 条增至 **103 条**；OpenAPI、生成客户端、权限矩阵与 Schema Registry 与实现同一批落库。

### 3. 一个事务内的完整删除编排

跨域编排放在 `apps/api/src/workflows/task-deletion.workflow.ts`（`TasksManagementModule` 不能反向依赖 `TaskGroupsModule` / `PublishedRecordsModule`，后者已依赖前者）。执行顺序与各自的副作用：

1. **授权与读取**：`TaskDeletionCommandPort.authorize`（项目可写 → 模块 / 功能归属 → 任务可读）→ 读取任务行（含 `row_version`）。
2. **软删除（提前拿行锁）**：`task-management.repository.softDelete` 条件更新 `deleted_at = now(), deleted_by = actor, row_version = row_version + 1 WHERE id = ? AND project_id = ? AND row_version = ? AND deleted_at IS NULL`，未命中即 409 `TASK_STATE_CONFLICT`。
3. **解除 GitHub 链接关联**：`ExternalLinksCommandPort.detachTarget(tx, projectId, "TASK", taskId)` 只删 `app.task_external_links` 关联行；`app.external_links` 的链接本体保留（同一 URL 若还被项目 / 功能 / 记录引用则照常显示，项目面板的聚合结果随之减少），返回删除行数写入 `removedLinkCount`。
4. **聚合组处理**：`TaskGroupDeletionPort`——该任务是 `SOURCE` 时自动标记 `DETACHED`（写入解除时间与原因），若是最后一个来源则同事务关闭聚合组（`CLOSED`）并解除 `MAIN`；该任务是 `MAIN` 时**拒绝**，返回 409 `TASK_GROUP_MAIN_LOCKED`「该任务是聚合组 {id} 的主任务，请先解除合并后再删除」（主任务被删会让组失去聚合锚点，属必须由人决定的动作，不做自动解除）。
5. **作废该任务的迭代记录**：`TaskRecordVoidPort.voidTaskRecords` 复用 `RecordLifecycleService` 的作废实现（`status = 'VOID'`、`voided_at` / `void_reason`），但**绕过 `transition` 的系统管理员硬门禁**（新增 `voidByTaskDeletion`）：删除任务本身即承担作废后果，普通项目成员删除任务时不需要管理员身份。作废是**状态变更**，记录与全部版本按 ADR-024 原样保留，可被管理员按既有恢复路径恢复（本 ADR 不提供任务侧恢复入口，但记录侧的恢复路径未被禁用）。
6. **审计**：`audit.append(tx, { action: "task.delete", targetType: "TASK", targetId, eventPayload: { projectId, moduleId, featureId, code, title, reason, voidedRecordCount, removedLinkCount, detachedGroupRole } })`，`sourceChainId = PROJECT:{projectId}`。
7. **动态**：`activity.updateEntityVisibility(..., sourceStatus: "DELETED", sourceRowVersion: expectedRowVersion + 1)`（让该实体此前的动态行随删除更新状态与版本，避免旧行残留为「有效」）→ `activity.append(tx, { activityType: "TASK_DELETED", ... })`，`visibilityScope: "MEMBER"`。
8. **搜索投影**：`SearchProjectionWritePort.remove(tx, projectId, "TASK", taskId)`——已删除任务的投影必须移除，否则全局搜索与命令面板会命中指向 404 的深链。

审计、动态、投影与业务写入使用同一 `TransactionContext`、同一事务提交或一同回滚（AGENTS.md 第 6 节）。

### 4. 可见性与读写收窄

- **删除后任务退出所有读路径**：25 处任务读查询（任务列表、任务中心 R-3、看板、聚合组 R-7、任务详情、成员任务、项目统计、搜索投影刷新等）统一补 `deleted_at IS NULL` 条件；`card-stat-columns.ts` 的 `effectiveTaskWhere` 与 `task-list-order.ts` 的排序前提同步收窄，因此删除任务同时退出完成率、逾期统计与任务中心卡片。
- **不新增状态位**：`work_status` / `lifecycle_status` 的取值域不变（删除是**第三维**，不是新的 `work_status`），避免污染 ADR-054 与 ADR-037 已冻结的状态机与看板口径。
- **项目动态与审计照常保留**：删除前该任务的动态行仍在（状态更新为 `DELETED`），删除本身写一条 `TASK_DELETED` 动态与 `task.delete` 审计，满足用户「项目动态和审计日志里面也需要有保留取消任务的记录」的要求。
- 删除后的任务在被删除时的 `work_status` 原样保留（`TODO` / `DONE` / `CANCELED` 都可能是删除前的状态），仅作为历史事实呈现在审计与响应里。

### 5. 幂等重放的授权口径

- 幂等重放**不能**再按任务可读性复核：任务行已软删除，任何带 `deleted_at IS NULL` 的可读性判定都会让**合法重放变成 404**。因此重放路径只复核：当前认证有效 → 缓存的 `projectId` / `moduleId` / `featureId` / `taskId` 与请求一致 → **原操作的写入门禁**（项目可写 + 模块 / 功能归属，不含任务可读性）。
- 实现上必须把这个区别落实到位：带 `taskId` 的授权复核只能出现在**首次执行**的 `execute` 里。`IdempotencyHttpService.run` 的 `actorId` 回调在**执行与重放两条路径都会运行**，把带任务可读性的授权放进去会让重放 404（本 ADR 实施过程中实测到的真实缺陷）。

### 6. 数据库

- 迁移 `0034_task_soft_delete.sql`：`app.tasks` 新增 `deleted_at TIMESTAMPTZ` / `deleted_by INTEGER`；`tasks_deleted_by_users_id_fk`（`REFERENCES app.users(id) ON DELETE restrict`）；`tasks_deleted_state_check`（两列同时为空或同时有值）；末尾校验存量数据一致性。
- 迁移 `0035_search_projection_delete_grant.sql`：`GRANT DELETE ON app.search_projection TO app_runtime`。**这是一处真实缺陷的修复**：`app.search_projection` 是纯派生检索缓存、不是业务历史，删除任务必须移除其投影，但 0001 的角色授权只给了 `SELECT, INSERT, UPDATE`，任何删除任务都会以 `permission denied for table search_projection` 500。授权只放开这一张派生表，业务表仍无 `DELETE`。
- `app_runtime` 对 `app.tasks` 仍只有 `SELECT, INSERT, UPDATE`（软删除走 UPDATE，不需要 `DELETE`），与「业务历史不物理删除」的口径一致。

### 7. 前端

- 任务编辑弹窗页脚（原「取消任务」位置）改为「删除任务」，点击后弹出**二次确认**（`AppModal` + `tone="danger"` + `Alert` 警示「不能恢复」），确认后调用删除接口；确认弹窗与编辑弹窗的层级关系必须让它在编辑弹窗内部渲染（两者互斥的渲染树会让确认弹窗永远不可见）。
- 任务详情动作行的「恢复任务」按钮删除；`TaskStatusPanel` 的 `CANCEL` / `RESTORE` 分支保留为兼容历史深链的不可达代码，不再提供入口；「取消任务不会物理删除」的旧提示文案删除（与新语义冲突）。
- 删除成功后失效任务、看板、聚合组、任务中心、模块 / 功能 / 项目统计、动态、通知、搜索、记录、链接等缓存，并调用 `invalidateShellCounters`（侧栏未完成与遗留问题计数）。

## 非目标

1. **不**提供任务还原入口，也**不**提供任务的彻底删除（用户已明确放弃；物理删除只随其所属项目的删除一并发生）。**2026-10-09 修订（[ADR-062](ADR-062.md)）**：项目层已改为物理删除，原 ADR-055 的「保留期自动清理」已整体下线，因此任务物理删除的触发只剩「项目被删」这一条。
2. **不**在还原 / 重新删除时重建已解除的链接关联，也**不**恢复已作废的迭代记录（用户答复「不做这个了」）。
3. **不**删除 `app.tasks` 行、`task_status_history`、`change_records` 与 `change_record_versions`、审计行或任何动态行。
4. **不**改 `CANCEL` 流转本身（`transitionTask` 的 `CANCEL` 分支与 `work_status = 'CANCELED'` 仍然存在、仍可用于历史数据与既有深链），只是前端不再提供入口。
5. **不**动项目层删除（ADR-049 / ADR-051 / ADR-055）与记录作废 / 恢复（ADR-024）的任何口径。**2026-10-09 修订（[ADR-062](ADR-062.md)）**：项目层删除本身已整体改为物理删除（ADR-049 / ADR-050 / ADR-051 / ADR-052 / ADR-055 全部下线），本项仅保留「本次任务删除不改动项目层」的原意。
6. **不**把删除做成可撤销的「软取消」：没有撤销窗口、没有前端内存态恢复。

## 影响与验证

- **数据库**：2 个迁移（0034 / 0035），无新表、无新角色；`app.tasks` 新增 2 列 + 1 个复合外键 + 1 个状态一致性 CHECK。
- **契约**：2 条新路由（Route Registry 101 → 103）、1 个新契约文件 `task-deletion.zod.ts`、权限矩阵补 `deleteTask` / `deleteModuleTask`、OpenAPI 与生成客户端同一批再生成（5 产物无漂移）。
- **后端**：`task-deletion.command-port.ts`、`task-deletion.workflow.ts`、`task-deletion-http.service.ts`、`task-deletion.controller.ts`、`task-group-deletion.port.ts`、`task-record-void.port.ts`（新增）；`tasks-management.service.ts`、`task-management.repository.ts`、`search-projection.write-port.ts`、`external-links.port.ts`、`record-lifecycle.service.ts`、`published-record.repository.ts`（扩展）；25 处读路径补 `deleted_at IS NULL`。
- **测试**：`apps/api/test/task-deletion.integration.test.ts` 9 例真实 PostgreSQL + HTTP（含事务性、链接解除、记录作废、聚合组自动解除与 MAIN 拒绝、If-Match 冲突、跨项目 404、幂等重放、删除后二次删除 404 且审计不重复）；Web 侧 `TasksPanel.test.tsx` 的「ADR-058 删除任务」用例覆盖「编辑弹窗无取消任务 → 删除任务 → 确认弹窗 → 未确认不调用接口 → 确认后带 `If-Match` 与幂等键调用」。另有断言级鉴别性验证：移除 `deleted_at IS NULL` 过滤后用例转红、恢复后转绿。
- **已知偏差**：Playwright 未覆盖删除任务的浏览器路径（本轮无前端 E2E 用例）；软删除的存量数据一致性与大批量删除的索引表现未做压测。
