# ADR-059 模块与功能删除：软删除并级联删除所含功能与任务

> **部分条款已被 ADR-096 替代（2026-10-23）**：模块与功能删除已从软删除改为物理删除，级联清除下级功能、任务、记录、版本、遗留项与链接关联；所属上级保留，未分类模块继续禁止删除。只保留审计、项目动态与顶层 `module.delete` / `feature.delete`。仍有效的权限、版本冲突与重放门禁口径继续沿用。

- 状态：Accepted
- 日期：2026-10-09
- 决策人：项目负责人（用户指示）与开发代理共同确认
- 关联：修订 [ADR-039](ADR-039.md) 的「项目内管理操作对全体活跃成员开放」清单；扩展 [ADR-049](ADR-049.md) 的软删除范式与 [ADR-058](ADR-058.md) 的单任务删除语义；沿用 [ADR-043](ADR-043.md) / [ADR-044](ADR-044.md) / [ADR-045](ADR-045.md) 的「模块与功能只有 ACTIVE」口径与 [ADR-008](ADR-008.md) 的审计只追加；与 [ADR-051](ADR-051.md) 的 `app.purge_project` 物理删除并列，互不替代（2026-10-09 注记：[ADR-051](ADR-051.md) 已由 [ADR-062](ADR-062.md) 替代，`app.purge_project` 窄口由 ADR-062 承继并成为项目删除的唯一实现，模块与功能的软删除则不受影响）

## 1. 背景

用户指示（原话）：

> 给模块和功能增加删除按钮，如果里面有功能或者任务，要提醒操作者是否删除，如果真的删除那就一起删

当前事实：

- [ADR-044](ADR-044.md) 与 [ADR-045](ADR-045.md) 先后下线模块层与功能层的归档，`app.modules.status` 与 `app.features.status` 被 CHECK 锁定为 `ACTIVE`、`archived_at` 被 CHECK 锁定为空。因此模块与功能**既没有归档态，也没有任何删除路径**——唯一的移除方式是整个项目被删除（[ADR-051](ADR-051.md) 的 `app.purge_project`，现由 [ADR-062](ADR-062.md) 作为项目删除的唯一实现）。
- `app_runtime` 对 `app.modules` 与 `app.features` **没有 `DELETE` 授权**（只授予 `SELECT` / `INSERT` / `UPDATE`），物理删除必须新增角色授权。
- `app.protect_unclassified_module()`（`database/migrations/0001_invariants_and_permissions.sql`）在 `BEFORE DELETE` 上拒绝物理删除 `kind = 'UNCLASSIFIED'` 的模块，`0031_project_purge.sql` 只为 `app.purge_project` 开了事务级旁路；`docs/permissions.md` 同时记录 2026-09-09 的人工确认「未分类模块……不能物理删除」。
- `app.modules` 每个项目恰好一个 `UNCLASSIFIED` 模块（`modules_one_unclassified_unique` 部分唯一索引 + `0001` 的每项目断言），它是模块级任务（`tasks.scope_type = 'MODULE'`）与「就地新建任务」的默认归属。
- 任务删除已有完整范式（[ADR-058](ADR-058.md)）：软删除 + 同事务解除链接关联、解除聚合组来源关系、作废该任务的已发布记录、写审计与项目动态、移除搜索投影。

## 2. 决策

### 2.1 删除一律是软删除

`app.modules` 与 `app.features` 各新增 `deleted_at` / `deleted_by` 两列（迁移 `0036_module_feature_soft_delete.sql`），并在同一迁移内加：

- 成对约束 `modules_deleted_state_check` / `features_deleted_state_check`：两列同时为空或同时有值；
- 外键 `modules_deleted_by_users_id_fk` / `features_deleted_by_users_id_fk`（`ON DELETE restrict`，指向 `app.users`）；
- 不新增索引（列表查询仍由既有的项目 / 模块外键索引驱动，过滤条件 `deleted_at IS NULL` 是索引后的残余过滤）。

理由：

1. 与 [ADR-049](ADR-049.md)（项目）与 [ADR-058](ADR-058.md)（任务）的既有范式一致，`app_runtime` 不需要任何新授权（`UPDATE` 已具备）；
2. 「不物理删除业务历史」是 [AGENTS.md](../../AGENTS.md) §6 的硬约束，模块与功能下面的任务、迭代记录与审计链都必须保留；
3. 软删除不需要触碰 `app.protect_unclassified_module` 触发器与 2026-09-09 的人工确认，物理删除则需要同时推翻这两条。

物理清除仍然只随所属项目的删除（[ADR-051](ADR-051.md) 的 `app.purge_project`，现由 [ADR-062](ADR-062.md) 作为项目删除的唯一实现）发生（原「保留期自动清理」已由 ADR-062 下线）。

### 2.2 未分类模块不可删除

`deleteModule` 对 `kind = 'UNCLASSIFIED'` 的模块返回 **409 `MODULE_UNCLASSIFIED_PROTECTED`**，前端对这类模块**不渲染删除入口**。

理由：未分类模块是模块级任务与「就地新建任务」的默认归属，删掉之后该路径没有可用的 module_id；它同时是「每项目恰好一个」的数据库不变量所保护的对象。本 ADR 的删除是软删除，与 `app.protect_unclassified_module()` 的**物理删除**禁令不冲突，二者并行生效：物理删除依然被触发器拒绝，软删除被本 ADR 显式拒绝。

### 2.3 级联范围

**删除模块**（`deleteModule`）在同一事务内处理：

| 对象 | 处理 |
| --- | --- |
| 模块下全部功能 | 逐个软删除（`deleted_at` / `deleted_by`） |
| 模块下全部任务 | 逐个走 [ADR-058](ADR-058.md) 的完整单任务语义（软删除 + 解除 GitHub 链接关联 + 聚合组 SOURCE 解除 / MAIN 拒绝 + 作废该任务的已发布记录 + 逐条审计与动态 + 移除搜索投影） |
| 模块自身的已发布记录（`module_id` 匹配、`status = 'PUBLISHED'`，含功能级） | 作废（`VOID`），复用记录域既有的作废副作用链 |
| 模块与功能 | 移除搜索投影（`search.remove`） |

**删除功能**（`deleteFeature`）在同一事务内处理：

| 对象 | 处理 |
| --- | --- |
| 该功能**自身的**任务（`scope_type = 'FEATURE' AND feature_id = ?`） | 逐个走 ADR-058 的完整单任务语义 |
| 该功能的已发布记录（`feature_id` 匹配） | 作废 |
| 功能自身 | 软删除 + 移除搜索投影 |

**模块级任务（`scope_type = 'MODULE'`）在删除功能时不被删除。** 它们归属模块，只是通过 `app.task_feature_impacts` 影响该功能——这与 `card-stat-columns.ts` 的 `taskScopeWhere(sql, "feature", …)`（功能卡计数**包含**影响该功能的模块级任务）必须区分开：计数口径包含影响关系，删除口径不包含。

影响关系行（`app.task_feature_impacts` / `app.change_record_feature_impacts`）**一律保留不删**：它们是业务历史（「这条迭代影响了哪些功能」），删除它们等于改写历史。指向已删除功能的引用由**读侧**过滤（见 2.5）。

「已发布记录」的作废数量按 `status = 'PUBLISHED'` 过滤，因此被任务级联先作废的记录不会被重复处理（记录状态已变为 `VOID`）。

### 2.4 权限：系统管理员或本项目组长

`deleteModule` / `deleteFeature` 是本 ADR 新增的 [ADR-039](ADR-039.md) 「项目内管理操作对全体活跃成员开放」的**第五处例外**，与 [ADR-049](ADR-049.md) 的项目删除同口径：

| 身份 | 结果 |
| --- | --- |
| 系统管理员 | 允许 |
| 本项目 ACTIVE 组长（LEADER） | 允许 |
| 本项目其他活跃成员 | 403 `MODULE_DELETE_FORBIDDEN` / `FEATURE_DELETE_FORBIDDEN` |
| 非成员 / 已移除成员 / 不存在或已删除的模块、功能 | 404（不泄露存在性） |

理由：一次删除会带走模块下的全部功能、全部任务及其迭代记录，破坏面远超「编辑名称」（ADR-039 放开的对象），与项目删除属于同一档权力；而它又不像彻底删除那样不可撤销（软删除仍可人工介入恢复），因此不照搬 [ADR-051](ADR-051.md) 的「仅系统管理员」。

组长身份用**实时**成员关系判定（`ProjectRoleGateService`），转移或移除后立即失效。

### 2.5 读侧收窄

删除后模块与功能必须**从全部读路径消失**。以下位置统一补 `deleted_at IS NULL`：

- 模块：`module-management.repository.ts`（列表 / 查找）、`postgres-module-query-port.ts`（写前检查）、`postgres-module-read-port.ts`（查找 / 名称 / 计数）
- 功能：`feature-management.repository.ts`（列表 / 查找 / 相似候选）、`postgres-feature-query-port.ts`、`postgres-feature-read-port.ts`、`external-link-target.port.ts`
- 统计：`card-stat-columns.ts` 的 `projectStatColumns`（活跃模块数、活跃功能数）、`moduleStatColumns`（活跃功能数）、`featureStatColumns`
- 聚合与投影：`external-links.repository.ts` 的项目链接聚合（功能来源）、`change-record-read.port.ts` 的功能名解析
- 记录的影响功能引用（`impactFeatureIds`）：`published-record.repository.ts`、`record-draft.repository.ts`、`record-publication.repository.ts` 三处列子查询改为只取**存活**功能

最后一条是刻意的取舍：影响关系行保留（历史），但记录详情不再展示指向已删除功能的影响项，避免死链。

### 2.6 一次性事务与锁序

一个命令只创建一个 `UnitOfWork`，全部写入显式共享同一个 `TransactionContext`。锁序沿用 [AGENTS.md](../../AGENTS.md) §6 与既有约定：

```
project FOR SHARE -> module FOR SHARE/FOR UPDATE -> feature FOR UPDATE（ID 升序）
  -> task FOR UPDATE（ID 升序）-> taskGroup（ID 升序）
```

先按父到子取得 `FOR SHARE` / `FOR UPDATE` 之后才进入任务聚合锁序，防止父级删除与子级写入竞态。`concurrencyPolicy.lockOrder` 登记为 `["project","module","feature","task","taskGroup"]`。

### 2.7 审计、动态与搜索

- 审计动作：`module.delete`（`targetType: "MODULE"`）与 `feature.delete`（`targetType: "FEATURE"`），payload 记录名称、编码、原因、级联计数（功能数 / 任务数 / 作废记录数 / 解除链接数）。
- 项目动态：`MODULE_DELETED` / `FEATURE_DELETED`（`visibilityScope: "MEMBER"`），并对模块 / 功能写入 `updateEntityVisibility(..., sourceStatus: "DELETED")`；级联删除的每个任务与每条作废记录另有各自的动态行，与 [ADR-058](ADR-058.md) / [ADR-024](ADR-024.md) 一致。
- 搜索：模块、功能逐个 `search.remove`（任务与记录由各自的既有路径处理）。
- **不发通知**（非目标，见 §4）。

### 2.8 重放授权

两条路由各自在 `ScopeDeletionHttpService` 内联一个 `replayAuthorizer`，读**保留**的成员关系（`ProjectRoleGateService` 的 `scopeDeleterReplayRole`，模块与功能两条路由共用同一个门禁方法）：删除成功后模块 / 功能行仍存在但已带 `deleted_at`，`manageRole` 的授权范围不受影响（项目未被删除），但资源级存在性复核会失败——**带资源存在性的授权只允许出现在 `execute` 内部**，`actorId` 回调只复核当前认证与角色，否则合法重放会退化成 404（[ADR-058](ADR-058.md) 实施中实测过的真实缺陷，本次在两条新路由上从一开始就按同一规则实现）。

### 2.9 确认弹窗的计数口径

前端确认弹窗**不新增预览接口**，用模块卡 / 功能卡已有的 `stats`：

- 模块：`stats.activeFeatureCount`（功能数）+ `stats.openTaskCount`（未完成任务数）→ 文案「该模块下包含 N 个功能、M 项未完成任务；确认删除后，模块内的**全部**功能与任务（含已完成、已取消）将一并删除，且无法恢复。」
- 功能：`stats.openTaskCount` + `stats.completedTaskCount` + `stats.recordCount`，文案同构。

**为何不给统计加 `taskCount`**：`ModuleItem` / `FeatureItem` 是 `createModule` / `updateModule` / `createFeature` / `updateFeature` 四条幂等路由的重放响应 Schema，给它们加字段属于「重放安全字段集合变化」，按 [AGENTS.md](../../AGENTS.md) §6 必须升级这四条路由的 `idempotencyContractVersion`，会让**在执行中的创建 / 编辑请求重放变成 409**——这是与「加一个删除按钮」无关的用户可见副作用，因此改用「已加载的近似计数 + 明确说明还会带走已完成 / 已取消任务」的文案，并在**删除成功后**把服务端返回的精确计数（`deletedFeatureCount` / `deletedTaskCount` / `voidedRecordCount` / `removedLinkCount`）显示在结果提示里。

### 2.10 响应

`ModuleDeletionResponse`：`id` / `projectId` / `code` / `name` / `kind` / `deletedAt` / `deletedBy` / `deletedFeatureCount` / `deletedTaskCount` / `voidedRecordCount` / `removedLinkCount`。

`FeatureDeletionResponse`：`id` / `projectId` / `moduleId` / `code` / `name` / `deletedAt` / `deletedBy` / `deletedTaskCount` / `voidedRecordCount` / `removedLinkCount`。

两条路由均为 `POST .../delete`（与 `deleteProject` / `deleteTask` 同形），`session` + `csrfPolicy: "required"` + `idempotencyRequired`（契约版本 `1.0.0`）+ `If-Match` 必填（版本门禁），`Content-Type` 必须为 `application/json`。

## 3. 影响

- **数据库**：新增迁移 `0036_module_feature_soft_delete.sql`；不新增授权（软删除走既有 `UPDATE`）、不删除任何数据、不修改历史迁移。
- **契约**：新增 Schema `DeleteModuleRequest` / `ModuleDeletionResponse` / `ModuleDeletionReplayContext` 与 `DeleteFeatureRequest` / `FeatureDeletionResponse` / `FeatureDeletionReplayContext`；Route Registry 由 103 条增至 **105** 条（`deleteModule`、`deleteFeature`）；权限矩阵同步 105 条；`pnpm contract:generate` 重生成 5 个产物。**既有路由的 `idempotencyContractVersion` 不变**（没有既有响应 Schema 变化）。
- **服务端**：新增跨域 Workflow `ScopeDeletionWorkflow`（模块 / 功能两条级联）+ HTTP 服务 + 控制器，注册进 `TaskCompletionModule`（该模块已经依赖模块、功能、任务、记录、链接、聚合组与搜索投影全部所需模块）；`TaskDeletionWorkflow` 抽出「在既有事务内删除单条任务」的入口供级联复用；`TaskDeletionCommandPort` 增加按作用域列举与锁定任务的读方法；记录域新增按作用域作废的公共端口；模块与功能的仓储增加软删除方法。
- **前端**：模块卡与功能卡 / 列表新增「删除」入口（仅系统管理员与组长可见），二次确认弹窗，成功提示带级联计数；新增动态与审计的中文标签。
- **非目标**：不提供模块 / 功能还原与彻底删除入口；不发通知；不删除影响关系行；不改任务删除、项目删除、记录作废的既有语义；不引入预览接口。

## 4. 未决与后续

- 恢复入口：本 ADR 不提供。若后续需要，必须新增 ADR 并同时确定「还原后任务与记录是否随之还原」（被级联删除的任务已软删除、记录已作废，语义上不能自动回滚）。
- 通知：删除模块 / 功能当前不通知项目成员，与 [ADR-058](ADR-058.md) 的任务删除一致。若改成通知，需先解决「删除后深链必成死链」（[ADR-035](ADR-035.md) 的通知只能标记已读、不能作废）。
- `featureStatsSchema.recordCount` 在功能被软删除后不再有任何渲染入口，未做清理；这是纯展示面的冗余，不构成数据不一致。

## 5. 验证

- 迁移：`pnpm db:migrations:check`；真实 PostgreSQL 18.6 + PGroonga 上跑 `0036` 的升级与约束行为（成对约束、外键、软删除后再删除的幂等拒绝）。
- 契约：`pnpm contract:generate` / `contract:drift` / `contract:validate`（105 条）/ `permissions:check`（105/105）。
- 真实数据库集成测试（`apps/api/test/scope-deletion.integration.test.ts`）：模块级联删除（功能数、任务数、记录作废、链接解除、聚合组解除、审计与动态、搜索投影移除）、未分类模块 409、普通成员 403、非成员 404、版本冲突 409、幂等重放、父级 FOR SHARE 与子级写入竞态、服务端计数与数据库剩余行一致。
- 前端单测：删除入口的角色可见性、确认弹窗文案、成功提示计数、缓存失效。
