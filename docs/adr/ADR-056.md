# ADR-056：维护中项目新建任务即回到进行中

- 状态：Accepted
- 基线固化：2026-10-08
- 接受依据：用户 2026-10-08 指示——「我要求如果给一个维护中的项目创建了一个新的任务，那么那个项目要转换为进行中」。
- 修订关系：**扩展 [ADR-035](ADR-035.md) 的自动升级路径**（新增「任务创建」这一触发点，与既有的「首次任务完成」并列）；**修订 [ADR-043](ADR-043.md) 第 7 节第 3 条的边界**（该条声明不改动 ADR-035 的自动升级口径，现由本 ADR 增加第二个触发点）。ADR-043 的三态取值、「进入维护中要求任务全部收尾」（§4）与「三态都可写」（§6）全部不变。**本 ADR 的触发面由 [ADR-057](ADR-057.md) 扩展为「任务重新变为未收尾」（新增 `TASK_REOPENED` / `TASK_RESTORED`），端口方法随之更名为 `reopenMaintenanceProject`；下方 §2 与 §5 非目标第 2 条的对应表述以 ADR-057 为准。**
- 关联：[ADR-054](ADR-054.md)（任务归档下线后，`countOpenTasks` 是唯一的有产出旁路，本次不引入新的旁路）、2026-09-30「维护中项目不产出任务中心卡片」（本次使该项目在创建任务后重新产出卡片）。
- 版本口径修订：[ADR-092](ADR-092.md) 起维护中回到进行中只改状态与 `updated_at`，保持 `row_version`；下方 §2 的旧 SQL 与测试证据保留为历史记录，当前实现以 ADR-092 为准。

## 背景

1. ADR-043 明确「维护中」的语义是**主体已完成、只做小修小补**，并要求进入维护中时项目下不存在未收尾任务。但进入之后项目仍然**可写**（§6「三态都可写」），因此可以在维护中项目里新建任务——这会把项目留在「维护中」却重新产生了待办，状态与事实不符。
2. ADR-035 已经确立「状态是事实的函数，而不是只能人工切换的标签」：项目下有任务首次完成时，若项目还是未开始，同一事务自动升级为进行中，并写审计、活动、搜索投影与开工通知。这条自动路径说明本项目在状态与事实冲突时选择**自动纠正状态**。
3. 「维护中 + 新任务」是同一类冲突的另一种形态：新任务意味着项目重新开工，项目不再是「只做小修小补」。因此修复方式与 ADR-035 一致——在同一事务里把状态切回进行中。
4. 反向不做：项目转进行中**不**回改任何任务（不自动恢复已完成任务、不自动取消新任务）；任务创建的成功与否也不受状态影响（三态都可写这一条不变）。

## 决策

### 1. 触发条件与范围

- 触发条件：命令执行前项目 `status = 'MAINTENANCE'`，且**任务创建成功**。只覆盖创建，不覆盖编辑、状态流转、合并/解除合并、记录发布等任何其它命令。
- 覆盖的创建入口：`createTask`（功能级）与 `createModuleTask`（模块级）走的是同一个 `TasksManagementService.execute()` 创建分支，因此四条真实调用路径全部生效——HTTP 直连、`TaskCreateCommandPort` 联合创建、`ProjectMemberTaskCommandPort`、`PostgresFollowupTaskCommandPort`（遗留问题转跟进任务）。
- 项目已经是 `NOT_STARTED` 或 `ACTIVE` 时**不发生任何事**：不写审计、不改版本、不推高 `row_version`。`NOT_STARTED` 的升级仍只由「首次任务完成」触发（ADR-035 不变）。

### 2. 同一事务内完成状态切换与全部副作用

- 切换由 `ProjectsWritePort.reopenMaintenanceProject`（原 `reopenMaintenanceProjectOnTaskCreate`，经 [ADR-057](ADR-057.md) 更名）承担，实现是**一条条件 UPDATE**：`... SET status = 'ACTIVE', updated_at = now() WHERE id = $1 AND status = 'MAINTENANCE' RETURNING ...`（ADR-092 修订：原实现同时递增 `row_version`，现保持版本不变。）。返回 `undefined` 表示未命中（不是维护中），调用方直接返回。（2026-10-09 修订：原表述含 `AND deleted_at IS NULL` 条件，该列随 [ADR-062](ADR-062.md) 删除项目软删除列一并消失（迁移 `0038`），条件已移除，命中语义不变。）
- 副作用与 ADR-035 的同事务写法逐项对齐：
  - 审计：`project.status.change`，`eventPayload` 含 `automatic: true`、`trigger: "TASK_CREATED"`、`taskId`、`before: { status: "MAINTENANCE" }`、`after: { status: "ACTIVE" }`；
  - 活动投影：`PROJECT_STATUS_CHANGED`，摘要「项目重新开工：{name} 由维护中回到进行中」，`metadata` 含 `trigger: "TASK_CREATED"` 与 `taskId`，`sourceStatus` / `sourceRowVersion` 取自切换后的项目行；
  - 搜索投影：`PROJECT` 实体按切换后的状态与行版本刷新（`source_row_version` 防旧写）；
  - 通知：**不写**。ADR-035 的口径是「只有『未开始 → 进行中』通知全体成员」，本 ADR 不扩大通知面。
- `first_task_completed_at` **不写**：它是「项目第一次有产出」的粘性标记，唯一来源仍是任务完成。伪造该标记会让「已有产出后不可回退未开始」这条不变量失去依据。

### 3. 并发与锁序

- 条件 UPDATE 只命中维护中的行：项目非维护中时不匹配任何行、**不取行锁**，也不会推高 `row_version`，因此重复创建不会造成版本空转。
- 创建路径此前已通过 `checkProjectForWrite` 对项目行持有 `FOR SHARE`；同一事务内的这条 UPDATE 由同一事务发起，属同行自持锁升级为写锁，不跨事务、不引入新的等待环，也不改变 AGENTS.md §6 的父级到子级取锁顺序。
- 两个并发创建任务：两个事务都持有 `FOR SHARE`，各自尝试升级为写锁，PostgreSQL 只能放行一个；另一个重新读取后发现项目已是 `ACTIVE`，条件 UPDATE 不命中 → 不重复写审计与活动。两个任务本身都正常创建。

### 4. 契约与接口面

- **不新增路由、不改任何 Schema 字段、不改幂等摘要输入与重放策略**，因此 `createTask` / `createModuleTask` 的 `idempotencyContractVersion` 保持 `3.0.0`；幂等重放按既有记录返回原响应，**不会**重复执行状态切换（副作用随首次执行生效一次）。
- 前端无需感知：项目卡片、项目详情与任务中心都从服务端读取状态，创建任务后刷新即可见。

### 5. 非目标

1. **不**改「未开始 → 进行中」的触发条件与通知口径（ADR-035 原样有效）。
2. **不**在编辑任务、推进任务状态、合并/解除合并、发布记录时切换项目状态——本 ADR 只有「新建任务」这一个动作代表重新开工。**（2026-10-08 由 [ADR-057](ADR-057.md) 修订：`REOPEN`（`DONE → TODO`）与 `RESTORE`（`CANCELED → TODO`）同样触发；`COMPLETE` / `CANCEL`、编辑、合并 / 解除合并与记录发布仍不触发。）**
3. **不**做反向自动：项目状态变化不影响任何任务的 `work_status` / `lifecycle_status`，也不解锁任何已取消或已完成的任务。
4. **不**发站内通知（沿用 ADR-035 的收窄口径）。
5. **不**回溯历史数据：存量「维护中但存在未收尾任务」的项目保持原状，人工切一次即可，不做迁移回填。
6. **不**放宽「进入维护中要求任务全部收尾」（ADR-043 §4，409 `PROJECT_MAINTENANCE_TASKS_OPEN`）——本次只是让「进了维护中又开工」这件事不会让状态与事实长期不符。

## 影响与验证

- **数据库**：无迁移、无新表、无新列、无权限变更；只使用 `app.projects.status` / `row_version` / `updated_at` 既有列。
- **契约**：无改动。Route Registry 仍为 101 条，OpenAPI 与生成客户端无漂移（`contract:drift` 5 产物）。
- **后端**：`projects/projects-write.port.ts`（新增 `ProjectMaintenanceReopenRecord` 与抽象方法 `reopenMaintenanceProject`）、`projects/postgres-projects-write-port.ts`（条件 UPDATE + 返回值映射）、`tasks/tasks-management.service.ts`（注入 `ProjectsWritePort`；`execute()` 创建分支调用 `reopenMaintenanceProject`，写审计 / 活动 / 搜索投影）。
- **测试装配**：`TasksManagementService` 新增构造参数后，`leftover-task` / `project-member-management-api` / `task-completion` / `tasks-api` / `task-create` 五个集成测试文件的装配同步补 `PostgresProjectsWritePort`。
- **测试证据**（本地 2026-10-08，真实 PostgreSQL 18.6 + PGroonga 于 `app_ci`）：
  - `apps/api/test/task-create-maintenance-reopen.integration.test.ts` **5 例**：① 维护中项目新建功能级任务后 `status='ACTIVE'`、`row_version` 递增、`first_task_completed_at` 仍为 `NULL`，审计恰一条且 `automatic/trigger/taskId/before/after` 齐全，活动与搜索投影的 `sourceRowVersion` 与切换后版本一致，**无** `project.status.change` 通知；同项目再建任务不推高版本、不重复写审计与活动；② 模块级任务（`createModuleTask`）同样触发；③ 未开始与进行中项目创建任务后状态与版本均不变、无审计与活动；④ 编辑任务不会把维护中项目拉回进行中；⑤ 任务创建与状态切换同事务，外层抛错后项目仍为 `MAINTENANCE`、无任务行、无审计、无活动、无搜索投影。
  - 鉴别性验证：临时停用 `execute()` 中的触发调用后，用例 ①② 转红（`expected 'MAINTENANCE' to be 'ACTIVE'`），用例 ③④⑤ 保持绿（负例与回滚不依赖触发点），恢复实现后 5 例全绿。
  - 回归：`apps/api` 单测 70 文件 405 例全绿；真实 PostgreSQL 集成 54 文件 **516 例**全绿；`pnpm --filter @inpulse/api typecheck` exit 0。
- **未覆盖 / 已知偏差**：并发创建只有一个事务能完成状态切换这一点由条件 UPDATE 与行锁语义保证，本批**没有**写并发的真库竞态用例（现有用例只覆盖串行重复创建）；`pnpm test:e2e`、契约重生成、整链 `pnpm check` 与 GitHub Actions 不在本批执行范围。

## 后果

- 项目状态与事实重新一致：「维护中」不会再长期挂着新任务；项目从「小修小补」变回「开工」，用户不需要手动切状态。
- 连带效果：按 2026-09-30 的口径，维护中的项目不产出任务中心卡片；创建任务后项目回到进行中，这些任务会重新出现在任务中心与任务看板中，属预期结果。
- 代价：状态切换是隐式副作用，用户可能没有主动点过「切换为进行中」；因此审计里显式写入 `automatic: true` 与 `trigger: "TASK_CREATED"`，项目动态也保留同一事实，保证「谁在什么时候、因为什么让项目回到进行中」可追溯。
- 若将来要把这个触发点收窄（例如只对功能级任务生效）或扩展（例如编辑任务也算重新开工），必须新增 ADR 修订并把实现位置（`TasksManagementService.execute()` 创建分支）、审计 `trigger` 取值与本节同步。
