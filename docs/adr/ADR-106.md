# ADR-106 项目群通知收敛为 Webhook-only

- 状态：Accepted
- 日期：2026-10-29
- 决策人：项目负责人（用户指示）
- 关联：取代 [ADR-105](ADR-105.md) 中 BOT 与 Webhook 并存、项目群绑定码和原项目群解绑路由的决策；保留 [ADR-077](ADR-077.md) 的个人绑定码与 [ADR-090](ADR-090.md) 的项目级通知开关；沿用 [ADR-093](ADR-093.md) 的群动态单一来源、[ADR-013](ADR-013.md) 的显式事务、[ADR-019](ADR-019.md) 的数据库级幂等、[ADR-070](ADR-070.md) 的加密 keyring 与 [ADR-104](ADR-104.md) 的 projectWecomGroup 能力门禁；新增迁移 0064_project_wecom_webhook_only.sql，路由总数 135 → 133

## 1. 背景

ADR-105 让项目群同时存在智能机器人 BOT 与群机器人 Webhook 两条通道。双通道带来三类长期成本：

1. 同一项目同时配置智能机器人和指向同一群的 Webhook 时会重复投递；
2. BOT 依赖单机器人单长连接、入群激活和绑定码兑换，运维与用户操作都更复杂；
3. 项目群绑定、通知开关、更换机器人和投递消费需要同时理解两种目标形状。

用户决定项目群通知以后只使用 Webhook。个人单聊机器人、个人绑定码、管理员机器人配置和个人通知保持不变。

## 2. 决策

### 2.1 项目群只保留 Webhook 路由

项目群 API 固定为：

- GET /api/v1/projects/{projectId}/wecom-group，operationId getProjectWecomGroup；
- PUT /api/v1/projects/{projectId}/wecom-group/notification-options，operationId updateProjectWecomGroupNotificationOptions；
- POST /api/v1/projects/{projectId}/wecom-group/webhooks，operationId createProjectWecomWebhook；
- DELETE /api/v1/projects/{projectId}/wecom-group/webhooks/{bindingId}，operationId deleteProjectWecomWebhook。

删除 createProjectWecomGroupCode 与 deleteProjectWecomGroup。旧路径 POST /projects/{projectId}/wecom-group/codes 和 DELETE /projects/{projectId}/wecom-group 不再注册，调用返回 404。securityFlow allowlist 从七条恢复到六条。

GET 状态只由 ACTIVE Webhook 决定：没有任何 ACTIVE Webhook 为 UNBOUND，至少一个为 BOUND。响应不再包含顶层 boundAt 与 boundByName，只返回 webhookTargets 和 notificationOptions。目标列表仍只暴露标签、URL 尾号、绑定时间、绑定人与最近投递错误。

项目群通知开关仍为五类：task.assign、task.status、record、project.member、scope.delete。保存开关前必须存在至少一个 ACTIVE Webhook，否则返回 409 PROJECT_WECOM_GROUP_NOT_BOUND；删除最后一个 Webhook 后，新保存与同 Key 重放都重新执行该门禁并返回 409。

### 2.2 数据库保留历史但不允许新 BOT

迁移 0064 不物理删除历史目标、绑定码或投递记录：

1. 历史 ACTIVE BOT 目标置为 REVOKED 并递增 row_version；
2. 所有未消费的项目群绑定码立即标记为已消费；
3. 历史 BOT 的 PENDING 投递置为 FAILED 并记录原因；
4. project_wecom_groups.channel_type 默认值改为 WEBHOOK；
5. 新增约束 project_wecom_groups_webhook_only_check，禁止任何新的 ACTIVE BOT；
6. app_runtime 失去项目群绑定码 INSERT、UPDATE 权限和兑换函数 EXECUTE 权限。

历史 BOT 行只用于审计与历史追溯，不参与状态、通知开关或投递。更换机器人函数 app.revoke_wecom_bindings_on_robot_change 仍撤销个人绑定，但不再修改项目群；为兼容现有响应字段，revoked_project_groups 固定返回 0。

### 2.3 桥接只消费 Webhook

正式与测试 VM 的 wecom-bridge 保持同一实现：

- bridge.mjs 物化项目群投递时只选择 channel_type = WEBHOOK 且 ACTIVE 的目标；
- long-conn.mjs 的 PENDING 查询只读取 WEBHOOK 目标，不再发送 aibot_send_msg 的 chat_type 2，也不处理项目群绑定码；
- Webhook URL 在数据库事务外用同一机器人 keyring 解密，AAD 仍为 app.project_wecom_groups.webhook_url；
- 每个 Webhook 目标独立 20 条/分钟限速，达到窗口时保持 PENDING 并让出其他目标；
- 图片、模板卡片与 Markdown 继续通过 Webhook 现有消息体发送；
- 群内文本消息不再兑换绑定码，机器人对群消息保持安静。

个人单聊仍由同一长连接消费 app.notifications，个人绑定码、欢迎语、主动推送和个人海报不改变。

### 2.4 审计与前端

Webhook 创建与删除继续写 project.wecomGroup.webhook.create / delete，开关保存继续写 project.wecomGroup.notificationOptions.update。审计不得记录完整 URL、Key 或密文。

项目成员页的企微卡片删除绑定码、倒计时、项目群解绑按钮和机器人链接入口，只保留 Webhook 添加、目标列表、删除与五类通知开关。标题改为群 Webhook 与通知设置。成员概览和管理员机器人设置中的项目群文案改为 Webhook 口径；管理员更换机器人只提示个人绑定会失效。

## 3. 非目标

- 不移除个人单聊智能机器人、个人绑定、管理员机器人配置或个人通知；
- 不自动创建企业微信群，不读取群列表，不管理 Webhook；
- 不迁移历史 BOT 投递，不补发历史群消息；
- 不新增按单个 Webhook 拆分的通知开关；
- 不改变五类项目群通知开关的物化边界和 MEMBER 可见动态来源；
- 不修改任何历史迁移或历史 ADR。

## 4. 后果与验收

- 项目群配置模型简化为多个 Webhook 目标，不再有项目群绑定码和重复投递风险；
- 旧 BOT 目标与绑定码在数据库中保留历史，但无法重新激活或兑换；
- 更换机器人不影响项目群 Webhook；
- 真实 PostgreSQL 与 HTTP 集成测试覆盖读权限、旧路由 404、Webhook 加密与脱敏、去重、删除隔离、通知开关门禁、重放门禁、机器人更换零撤销和数据库拒绝 ACTIVE BOT；
- 桥接静态检查确保不再引用项目群绑定码兑换、BOT 群发送和 chat_type 2；
- 契约、权限矩阵、测试矩阵与设计文档同步到 133 条路由和六条 securityFlow。

## 5. 迁移与回滚

迁移 0064 执行前必须确认测试 VM 与正式桥接已能处理 Webhook-only 队列。回滚只允许恢复上一发布镜像与只读迁移前的数据库备份，不允许把历史 BOT 目标重新置为 ACTIVE；若需要重新启用 BOT，必须新增 ADR 取代本决策。
