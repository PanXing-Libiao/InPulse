# ADR-088 离职账号物理删除与历史身份快照

- 状态：Accepted
- 决策日期：2026-10-20
- 接受依据：用户明确要求离职账号采用直接物理删除，而不是墓碑化；同时要求删除后审计日志、项目动态及历史业务记录仍能保留事件当时的账户名。此前落地的 [ADR-082](ADR-082.md) 墓碑化机制由本 ADR 取代，成员页「启用 / 已停用/离职」筛选继续有效。
- 关联：替代 [ADR-082](ADR-082.md) 的删除机制，延续 [ADR-086](ADR-086.md) 的审计操作人快照与 [ADR-087](ADR-087.md) 的项目动态操作人快照；新增迁移 `0050_audit_actor_snapshot.sql`、`0051_activity_actor_snapshot.sql`、`0052_actor_identity_snapshots.sql` 与 `0053_physical_user_delete.sql`；沿用 [ADR-013](ADR-013.md)（事务边界）、[ADR-019](ADR-019.md)（数据库级幂等）、[ADR-031](ADR-031.md)（管理员门禁）与 [ADR-083](ADR-083.md)（不再提供强制退出）。

## 1. 背景

墓碑化通过保留 `app.users` 行维持历史外键，但账号本身、登录名占用和个人资料仍然存在，不能算真正删除。离职人员清理要求删除账号行，同时不得让已发生的审计、项目动态、项目成员历史、任务、迭代记录、遗留项、外部链接和导入记录失去署名。

审计事件和项目动态不能依赖被删除的用户行。业务历史也不应在用户改名后悄然显示另一个姓名。因此需要把删除动作、私有运行态数据的级联清理、业务历史行与事件时身份快照分开设计。

## 2. 决策

### 2.1 物理删除入口

- `deleteUser` 仍为 `POST /api/v1/admin/users/{userId}/delete`，完整管理员 Session、CSRF、`Idempotency-Key` 与 `If-Match` 不变。
- 前置条件：
  - 目标账号存在且已 `DISABLED`；未停用返回 409。
  - 目标不是当前操作者。
  - 目标没有任何 `ACTIVE` 项目成员关系；否则返回 409 `ADMIN_USER_ACTIVE_PROJECT_MEMBERSHIP`。
  - `If-Match` 与目标 `row_version` 一致。
- 成功返回 204。新请求删除已不存在的用户返回 404；同一幂等 Key、同一摘要与同一契约版本的重放仍返回 204，且不重复写审计。
- 删除、身份留档、Session 撤销和 `admin.user.delete` 审计在同一 `TransactionContext` 内完成。审计载荷记录删除前身份 `before`、`after: null`、`physicalDeleted: true` 与撤销 Session 数。
- `deleteUser` 的幂等契约升至 `2.0.0`，重放授权策略为 `actorOnly`：用户行已不存在，不能再用目标用户资源做重放授权复核。

### 2.2 数据库边界

- 迁移 `0053_physical_user_delete.sql` 增加 `app.deleted_user_identities`，仅保存 `user_id / name / login_name / deleted_at`；该表不是可登录账号，不参与认证、授权、成员关系或负责人判定。
- `app.users` 的 `BEFORE DELETE` 触发器在删除前写入最小身份留档；删除后原登录名可由新账号复用。
- 删除 `app.users` 会将用户私有运行态数据级联删除：Session、CSRF Token、TOTP、恢复码、幂等记录、通知、企业微信绑定码和个人企业微信绑定，共 7 个 `ON DELETE CASCADE` 外键。
- 其余指向用户的业务外键全部移除。项目、成员历史、模块、功能、任务、负责人、任务状态历史、迭代记录、遗留项、外部链接、文档导入、AI 设置、企业微信机器人与项目群配置保留原用户编号作为历史坐标，不因删除账号而删除。
- 删除能力只通过 `SECURITY DEFINER` 函数 `app.delete_user_account(integer, integer)` 暴露给 `app_runtime`；运行时角色不获得 `app.users` 的表级 `DELETE`。函数在锁内复核身份、状态、版本与 ACTIVE 项目成员关系，失败时整笔事务回滚。

### 2.3 历史身份快照

- `0052_actor_identity_snapshots.sql` 为 26 个需要长期展示用户姓名的业务列增加 JSONB 快照，统一结构为 `{ id, name, loginName }`，并由 `app.capture_actor_identity_snapshot()` 在对应用户编号 INSERT 或变化时刷新。
- 快照在生产写入时固化，只用于展示和溯源；读取历史署名时优先使用快照，不因用户后续改名或物理删除而变化。
- 已覆盖项目创建人/删除人、成员关系、模块、功能、任务创建人、任务负责人、任务状态变更人、任务组、任务组成员、记录作者/处理人、记录版本、遗留项、遗留项转任务、外部链接、文档导入操作人、AI 设置更新人、企业微信配置操作人及项目归档请求。
- 审计由 `eventPayload.actorSnapshot` 自包含，项目动态由 `activity_projection.actor_snapshot` 自包含；二者分别遵循 ADR-086 与 ADR-087。
- 迁移会回填当前仍存在的业务行。若某个旧行没有快照且对应用户已经被删除，读取层可使用 `deleted_user_identities` 回退显示名；旧审计在 ADR-086 之前没有操作人快照，其行与哈希链仍保留，但无法自动恢复当时姓名。

### 2.4 读取与界面

- 任务状态历史直接读取 `changed_by_snapshot`；功能、正式记录、草稿、遗留项、记录清单与迭代总结优先读取对应身份快照。
- 目标用户删除后，管理成员列表不返回该用户；成员页「启用 / 已停用/离职」筛选保持，已停用账号仍可执行强制删除。已删除账号不出现在任何筛选。
- 审计页使用管理员的完整用户目录（包含已停用账号）解析无快照的旧审计与操作人筛选，避免账号停用后历史记录退化成「用户 #id」；已物理删除账号的新审计继续使用事件快照。
- 删除确认明确提示这是不可恢复的物理删除，同时说明审计、项目动态与历史署名会保留。
- 「强制退出」按 ADR-083 保持移除，本 ADR 不恢复该入口。

## 3. 非目标

- 不删除或重写审计事件、项目动态、项目成员历史、任务、迭代记录及其他业务历史。
- 不把 `deleted_user_identities` 或历史快照用于登录、权限、成员关系或任务负责人判定。
- 不恢复墓碑化、不提供账号还原，也不支持通过历史快照重建账号。
- 不自动删除企业微信机器人、项目群配置、文档导入结果或外部链接。
- 不为 ADR-086 之前的旧审计伪造当时姓名，也不重算历史 HMAC。
- 不改变停用前的任务交接流程；删除仍要求账号先停用并移出全部项目。

## 4. 后果与验收

- 原登录名在物理删除后释放，新员工可以复用；旧账号的 `sso_subject` 不再存在，不会与新账号绑定。
- 已删除用户的历史记录不再有指向 `app.users` 的外键，但保留稳定的用户编号和历史姓名快照。
- 定向验证必须覆盖：未停用 409、仍有 ACTIVE 成员 409、物理删除成功、7 类私有数据级联清零、业务历史与快照保留、删除后 404、同 Key 重放 204 且审计不重复、旧 Session 401、登录名复用和数据库无表级 DELETE 权限。
- 契约与生成物必须同批更新；路由总数保持 126，`deleteUser` 的幂等契约版本为 `2.0.0`。
