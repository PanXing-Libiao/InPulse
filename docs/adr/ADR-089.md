# ADR-089：停用账号前的项目组长移交

- 状态：Accepted
- 决策日期：2026-10-20
- 接受依据：用户 2026-10-20 指示「接下来我们更改停用界面，增加一个可能性，假如停用账号是其中项目的组长，则需要有一个口子进行组长移交选择，只能选择当前项目内已存在的负责人」。
- 关联：修订 [ADR-084](ADR-084.md)（把停用前的交接范围从任务扩展到项目组长身份）；沿用 [ADR-013](ADR-013.md)（单事务）、[ADR-019](ADR-019.md)（数据库级幂等）、[ADR-029](ADR-029.md)（契约响应与统一错误）、[ADR-031](ADR-031.md)（管理员门禁）、[ADR-053](ADR-053.md)（组长唯一性与转移）。

## 1. 背景

- 停用账号时，账号可能仍是某些项目的 ACTIVE 组长（LEADER）。ADR-053 要求有活跃成员的项目恰好保留一名 ACTIVE 组长，但停用账号不会移除其项目成员行，因此这些项目会留下一个无法继续履职的组长。
- ADR-084 的停用交接只处理 TODO 任务：没有未完成任务时弹窗直接显示「全部项目已完成」，管理员无法在停用流程内处理组长身份。
- 用户要求把组长移交放进同一个停用弹窗，并且新组长只能从该项目已有的活跃成员中选择，不能凭空创建账号或项目外成员。

## 2. 决策

### 2.1 复用停用接口，不新增路由

- 不新增组长移交路由；复用现有 `getAdminUserOffboarding` 读取交接清单，复用 `disableUser` 在同一个事务内提交任务动作与组长移交。
- `AdminUserOffboardingProject` 新增必填布尔字段 `requiresLeaderTransfer`。只要目标账号仍是该项目的 ACTIVE LEADER，项目就必须出现在交接清单中，即使它没有任何 TODO 任务。
- 组长项目仍返回该项目的 ACTIVE 成员列表，排除待停用账号与已停用账号；这些成员同时是任务接手人和新组长的候选来源。
- `AdminUserDisableRequest` 新增 `leaderTransfers` 数组，元素为 `{ projectId, newLeaderUserId }`，最多 1000 项且按 projectId 去重；`disableUser` 幂等契约版本由 2.0.0 升至 3.0.0。

### 2.2 服务端校验

在读取交接清单并锁定目标用户后，服务端必须：

1. 每个 `requiresLeaderTransfer = true` 的项目必须恰好提交一条组长移交；缺失返回 422 `ADMIN_USER_OFFBOARDING_LEADER_REQUIRED`。
2. 同一个项目不能重复提交；重复返回 422 `ADMIN_USER_OFFBOARDING_DUPLICATE_LEADER_PROJECT`。
3. 非组长项目提交移交返回 422 `ADMIN_USER_OFFBOARDING_LEADER_NOT_REQUIRED`。
4. 新组长等于待停用账号返回 422 `ADMIN_USER_OFFBOARDING_SELF_LEADER`。
5. 新组长必须是该项目当前 ACTIVE 成员（且不是待停用账号），否则返回 422 `ADMIN_USER_OFFBOARDING_LEADER_INVALID`。
6. 组长移交按 projectId 升序执行，位于任务改派/删除之后；全部交接完成后重新读取清单，只有清单为空才继续停用。

### 2.3 组长移交事务边界

- 新增 `ProjectLeaderTransferPort`，由项目模块提供 PostgreSQL 适配器；`AdminUserService` 通过该端口调用，不直接操作项目成员表。
- 端口在调用方传入的同一个 `TransactionContext` 内先锁定原组长与目标成员行，复核原账号仍为 ACTIVE LEADER、目标仍为 ACTIVE 成员，再复用 `ProjectsWritePort.setMemberRole` 的既有转移语义（先降原组长、再提升目标）。
- 移交写 `project.member.role.set` 审计，载荷包含 `previousLeaderUserId`；同时写 `PROJECT_MEMBER_ROLE_CHANGED` 项目动态。审计、动态、任务交接、会话撤销与账号停用必须共同提交或共同回滚。
- 端口拒绝把组长移交给项目外成员或待停用账号；项目不存在、组长身份已变化与目标成员无效分别返回明确的 404 / 409 / 422，最终由 `AdminUserService` 映射为统一的管理员停用错误。

### 2.4 前端停用弹窗

- 项目卡在标题区显示「需移交组长」标记；需移交组长的项目排在只有任务交接的项目之前。
- 每个组长项目内增加「项目组长移交」区块，使用成员选择器列出该项目的 ACTIVE 成员；默认不预选，必须由管理员明确选择一名新组长。
- 未选择新组长时「确认停用」保持禁用；底部提示同时统计未处理任务与未移交组长项目。
- 即使项目没有未完成任务，只要需要移交组长，也必须显示交接列表，不能显示「全部项目已完成」空态。
- 项目内没有其他可接手的启用成员时，显示明确提示并保持「确认停用」禁用；管理员需要先补充项目成员，再回到停用流程完成移交。

### 2.5 错误与并发

- 组长移交与原任务交接在同一管理员停用事务内完成；任一组长项目缺失、目标失效或并发变化都整体回滚，账号保持启用、Session 不撤销。
- 并发停用或并发组长转移时，后提交事务根据重新读取的组长状态返回 409 或 422，不允许静默覆盖。
- 重复请求仍由现有数据库级幂等保护；由于请求语义已变化，幂等契约版本升至 3.0.0，旧 Key 在新契约下返回 409。

## 3. 非目标

- 不自动指定新组长，不做轮询、按最早加入成员继任或后台异步移交。
- 不因停用自动把账号移出项目，也不自动创建新用户或项目成员。
- 不新增数据库迁移；组长身份与成员关系继续使用既有 `project_members` 模型和 ADR-053 的延迟约束。
- 不改变任务交接、账号停用、会话撤销与物理删除的既有规则。

## 4. 后果与验收

- 路由总数保持 128；`permissions:check` 仍为 128 条操作 / 128 条路由。
- API 单元测试覆盖停用请求体透传与组长相关错误映射。
- 真实 PostgreSQL 集成覆盖：组长项目未移交返回 422；移交给项目活跃成员成功并完成停用；移交给项目外成员返回 422；无任务但为组长的项目仍进入交接清单。
- Web 单元测试覆盖：组长项目显示移交控件；未选择新组长时确认禁用；选择后请求体包含 `leaderTransfers`；无任务但需移交组长时不显示完成空态。
