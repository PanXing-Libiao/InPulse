# ADR-035：项目生命周期四态（未开始 / 进行中 / 维护中 / 已归档）

- 状态：Accepted
- 基线固化：2026-09-17
- 收紧：收紧 [ADR-034](ADR-034.md) 中「归档要求项目 ACTIVE、恢复要求项目 ARCHIVED」与「项目写入口要求项目 ACTIVE」的表述；ADR-034 的申请—审核双人同意流程、任务 / 模块 / 功能归档口径不变。同步收紧 [功能设计 V1.1](../../功能设计v1.1.md) §9.3 / §9.4 / §9.5 / §10.2 / §11.2 中「项目状态默认正常、正常 / 未开始 / 已归档三态」的表述。
- 修订：决策 3 的角色口径经 [ADR-039](ADR-039.md) 修订——项目内管理权对全体活跃成员等同，`LEADER` 不再单独授权，`PROJECT_ADMIN` 已移除。
- 版本口径修订：[ADR-092](ADR-092.md) 起纯项目状态变更保持 `row_version`，首次任务完成因写 `first_task_completed_at` 仍递增版本；下方关于旧触发器「每次 UPDATE 恰好 +1」的表述按 ADR-092 解释。

## 背景

1. 改造前项目在库里只有 `ACTIVE` 与 `ARCHIVED` 两态，「未开始 / 正常」是前端按「作用域内有没有已完成任务」推导出来的展示标签，与存储状态不一致：同一个 `ACTIVE` 项目在不同页面可能显示成不同档位，列表排序也依赖派生值，无法按状态稳定筛选与统计。
2. 业务需要区分三种活跃语义：还没开工（未开始）、正在迭代（进行中）、主体已完成并只做小修小补且不打算归档（维护中）。第三种既不该被当成「进行中」继续排期，也不该被强制归档成只读。
3. 归档恢复后的状态在改造前是「回到 ACTIVE」，但 ACTIVE 在新模型里语义收窄为「进行中」，因此需要明确恢复后的落点与首个任务完成时的自动升级规则。

## 决策

### 1. 项目四态与唯一真相

```text
NOT_STARTED   未开始   项目下还没有任何已完成任务
ACTIVE        进行中   项目已开工
MAINTENANCE   维护中   主体已完成、只做小修小补且不打算归档（纯标签，不限制任何操作）
ARCHIVED      已归档   项目及其下级只读
```

- `app.projects.status` 是唯一真相，四态由 `projects_status_check` 约束；前端标签、列表排序与筛选一律直读存储状态，不再由完成任务数派生（模块与功能仍按各自作用域的任务完成情况派生，只是把「正常」改称「进行中」）。
- 新建项目从未开始起步，`app.projects.status` 默认值改为 `NOT_STARTED`。
- 列表排序固定为：进行中 → 未开始 → 维护中 → 已归档。

### 2. 粘性标记：项目出现过产出就不再回退未开始

- `app.projects.first_task_completed_at` 是永不回落的粘性标记，第一次有任务完成时置位（取最早一次完成时间），此后`LEAST()` 只保留更早值。
- 项目内出现过已完成任务后，不允许把项目回退为未开始（409 `PROJECT_STATUS_NOT_STARTED_LOCKED`），数据库兜底约束 `projects_not_started_lock_check` 同样拒绝该组合。
- 保留自动升级：项目处于未开始时，第一个任务完成会在同一事务内把项目升级为进行中并递增 `row_version`；其余状态只补粘性标记。`app.projects` 的 `row_version` 触发器要求每次 UPDATE 恰好 +1，因此置位语句用 WHERE 只命中真正需要变更的行——粘性标记已存在且项目不再是未开始时整条语句不写任何行，项目版本与 `updated_at` 都不动，后续任务完成不会反复推高项目版本，也不会作废在途的项目编辑 `If-Match`。ADR-092 起纯状态切换同样保持 `row_version`；固定版本的触发器兜底已由迁移 `0057_project_status_version_semantics.sql` 改写。

### 3. 手动切换的角色、可达边与错误码

- 允许主体：系统管理员，或本项目内当前活跃的成员（[ADR-039](ADR-039.md) 起角色不再区分管理权，`LEADER` 与 `MEMBER` 同等）；非成员或跨项目统一 404，不再有 403 角色分支。
- 可达边：未开始 ⇄ 进行中 ⇄ 维护中。禁止未开始与维护中直接互改（双向拦截，409 `PROJECT_STATUS_LEVEL_SKIP`），必须先经过进行中。
- 归档不是手动切换的目标：变更接口只收三个非归档目标态，ARCHIVED 仍走 ADR-034 的申请—审核流程；项目已归档时变更接口返回 409 `PROJECT_ARCHIVED`，必须先恢复。
- 恢复一律回到进行中（不回到归档前的状态），与「有产出就不回退未开始」的粘性规则一致。
- 状态变更不要求填写原因（归档仍要求原因）；CSRF、`Idempotency-Key` 与 `If-Match` 乐观锁必填，版本不符 409 `PROJECT_VERSION_CONFLICT`，目标与当前相同 409 `PROJECT_STATE_CONFLICT`。ADR-092 起纯状态变更保持 `row_version`，`If-Match` 继续保护内容并发，状态并发由项目行锁与三态规则串行化。

### 4. 通知与审计

- 只有「未开始 → 进行中」通知全体活跃成员（手动切换与首个任务完成触发的自动升级共用同一文案，通知类型 `project.status.change`）；维护中与其它迁移都不通知，避免在「进行中 / 维护中」之间反复切换时刷屏。
- 状态变更同事务写审计 `project.status.change`、活动 `PROJECT_STATUS_CHANGED` 与搜索投影；自动升级的事件负载带 `automatic: true` 与 `trigger: TASK_COMPLETED`。

### 5. 写入口口径：只有已归档拦截写入

- 项目四态之后，「项目可写」不再等价于「项目 ACTIVE」，而是「项目不是已归档」：未开始、进行中、维护中三态都允许建模块、建功能、建任务与写记录，维护中不限制任何操作（否则「未开始项目里不可能有第一个任务完成」会自相矛盾）。
- 父级写前检查（`ProjectAccessQueryPort.checkProjectForWrite`）只在 `ARCHIVED` 时返回 `parent-not-active`，模块、功能、任务、记录等下游沿用既有 409 语义。
- 外部链接的目标可写判定（`ExternalLinkWorkflow.target`）同步从「目标 ACTIVE」改为「目标不是已归档」：项目目标读四态，功能与任务是 `ACTIVE` / `ARCHIVED` 两态，改写后语义等价，原先被误判为只读的未开始 / 维护中项目恢复正常写入。

### 6. 存量迁移

- 迁移 `0017_project_status_lifecycle.sql`：任务状态历史里出现过完成快照的存量项目 → 进行中；其余原 ACTIVE 项目 → 未开始；已归档项目状态不变，只补 `first_task_completed_at`。
- 迁移不递增 `row_version`、不写审计，属于数据迁移而非用户动作。迁移后展示标签与改造前完全一致，差别只在于标签来源从派生改为存储。
- 但 `app.projects` 的 `projects_row_version` 触发器要求每次 UPDATE 恰好 `row_version + 1`，纯回填写法在有存量项目行的库上会被拒绝（`projects.row_version must advance exactly once`）；迁移因此在回填前后临时 `DISABLE` / `ENABLE` 该触发器。回填会挂起 `projects_bootstrap_complete` 这个延迟约束触发器的事件，必须先 `SET CONSTRAINTS ALL IMMEDIATE` 结算才能对同一张表再执行 `ALTER TABLE`。整个迁移在单个事务内执行，失败回滚不会留下被关闭的触发器。空库（CI 与集成测试）上这段逻辑是空操作，因此只有在真实存量库上才暴露。该历史触发器的「每次 UPDATE 恰好 +1」口径已由 [ADR-092](ADR-092.md) 修订为纯状态可保持版本；`0017` 的历史迁移不改。

## 影响与验证

- 迁移：`0017_project_status_lifecycle.sql`（四态 CHECK、默认值、归档约束改写、`first_task_completed_at` 与回填、未开始锁定兜底约束）。
- 契约：新增 `ProjectStatus` 与 `ProjectStatusChangeRequest` Schema Registry 条目；`ProjectItem` / `ProjectListItem` 增加 `hasCompletedTask`；`CreateProjectResponse.project.status` 由 `ACTIVE` 改为 `NOT_STARTED`；新增路由 `changeProjectStatus`（PATCH /api/v1/projects/{projectId}/status，审计动作 `project.status.change`）。
- 权限矩阵：`docs/permissions.md` 新增「变更项目状态」行，并把项目相关行的「项目必须 ACTIVE」改为「项目必须未归档（ADR-035）」。
- 前端：`features/common/resource-lifecycle.ts` 拆出项目四态标签与配色（未开始青 / 进行中主色 / 维护中紫 / 已归档琥珀）；编辑项目弹窗新增独立「保存状态」入口，越级与粘性锁定在界面上置灰并给出原因，服务端仍独立校验。
- 测试：单元层 `resource-lifecycle.test.ts`（四态标签与配色）、`project-management.service.test.ts`（角色门禁、越级、粘性锁、通知）、`project-management-modals.test.tsx`（置灰理由、保存状态请求头、无权限只读）；集成层 `project-management-api.integration.test.ts`（F-06.3 状态变更全路径）、`project-access.integration.test.ts`（未开始 / 维护中不再拦截写入）、`projects-read-api.integration.test.ts`（四态排序）、`task-completion.integration.test.ts`（首任务完成的自动升级、粘性置位与开工通知）。

## 未决与边界

- 维护中不设自动回收：项目停留在维护中不会被动归档，也不影响任何写入与统计口径。
- 未开始与维护中都允许写入，「未开始」因此不能当作写保护；需要只读请使用归档。
- 项目状态不影响模块与功能的归档条件与排序口径（模块与功能仍按各自作用域的任务完成情况派生「进行中 / 未开始」）。
