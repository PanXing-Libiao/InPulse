# ADR-091 项目封箱彩蛋：首次进入维护中时冻结快照并通过企业微信推送纪念海报

- 状态：Accepted
- 决策日期：2026-10-20
- 接受依据：用户要求项目进入维护中即视为基本完成，并设计一个机器人推送的项目完成彩蛋。用户确认个人单聊与项目群推送并存，每个项目终生只发生一次，且需要能体现项目成果与参与感的海报，不接受只发一行文字的简化方案。
- 关联：扩展 [ADR-035](ADR-035.md) 的项目生命周期、[ADR-043](ADR-043.md) 的维护中门禁、[ADR-077](ADR-077.md) 的项目群投递与 [ADR-090](ADR-090.md) 的项目群通知开关；沿用 [ADR-013](ADR-013.md) 的显式事务、[ADR-014](ADR-014.md) 的脱敏项目动态、[ADR-054](ADR-054.md) 的有效任务口径与 [ADR-088](ADR-088.md) 的身份快照原则；新增迁移 `0056_project_wraps.sql`。不新增 API 路由。

## 1. 背景

项目进入维护中表示主体交付完成，但既有系统只写一条状态变化动态和个人通知，无法形成一个有记忆点的完成时刻。用户希望在企业微信机器人通知中增加“项目封箱”彩蛋：既要清楚告诉项目群“这件事完成了”，也要让每个参与者在个人会话里看到与自己相关的纪念海报。

彩蛋必须只发生一次。项目后续可能因为缺陷或新需求回到进行中，再次进入维护中时不能重复封箱；升级前已经处于维护中的历史项目也不追溯。海报数据必须在封箱时冻结，否则成员、任务和记录继续变化后，同一项目的纪念内容会随查询时间漂移。

## 2. 决策

### 2.1 唯一触发条件

仅当一次项目状态写入同时满足以下条件时封箱：

1. 状态从非维护中切换为 `MAINTENANCE`；
2. 项目下没有未完成且未取消的有效任务，满足既有维护中门禁；
3. 至少有一个有效、未删除且未处于无效生命周期状态的已完成任务，继承项目卡的有效任务口径；
4. `app.project_wraps` 尚无该项目行。

因此，只有“已完成任务、没有未收尾任务”的项目会封箱；只有已取消任务或从未产生任务的项目只走普通维护中状态变化。首次封箱后，无论项目重开多少次、任务此后如何变化，都不再生成第二条封箱快照、封箱动态或封箱通知。迁移上线前已处于维护中的项目不补发。

### 2.2 冻结快照

迁移 `0056` 新增 `app.project_wraps`，以 `project_id` 为主键，保存：

- `sealed_at`、`sealed_by` 与不可变 `sealed_by_snapshot`；
- `template_version`，当前为 1；
- `snapshot` JSONB，包含项目编码与名称、完成任务 / 已发布记录 / 活跃成员 / 活跃模块 / 活跃功能 / 未收尾任务、持续天数、完成百分比、成员列表与关键时间线。

表只允许 `INSERT` 与 `SELECT`；`app_runtime` 没有 `UPDATE` / `DELETE`，`app_backup` 只读。项目物理删除时由外键级联清理，项目删除后不保留指向已不存在项目的封箱行。数据库 CHECK 约束校验快照基本结构、模板版本、操作人身份快照与大小上限。

快照在项目状态更新后的同一事务内，通过一条 `INSERT ... SELECT ... ON CONFLICT DO NOTHING` 生成。并发重复进入维护中时，主键与 `ON CONFLICT` 保证至多一条；只有真正插入成功的请求才继续写动态和通知。

### 2.3 审计、动态与个人通知

- 审计仍使用既有 `project.status.change` 动作，在 `eventPayload` 增加 `wrapped: true`、`wrapTemplateVersion` 与封箱统计；不新增第二套状态审计链。
- 首次封箱的项目动态类型为 `PROJECT_WRAPPED`，可见性为 `MEMBER`，摘要包含完成任务、发布记录、参与人数和持续天数。重复维护不满足快照插入条件时仍写普通 `PROJECT_STATUS_CHANGED`。
- 同一事务给全部项目活跃成员写 `project.wrapped` 站内通知，接受个人通知写入端既有的偏好过滤与去重规则。
- 个人设置不新增开关：`project.wrapped` 归入既有「项目开工 / 状态变化」设置。迁移把已关闭 `project.status.change` 的用户同步生成 `project.wrapped` 抑制项；用户重新开启该设置时整组删除。

### 2.4 企业微信个人单聊

`bridge.mjs` 识别 `project.wrapped` 后读取冻结快照，发送两段消息：

1. Markdown 文案「这一箱，有你的名字。」及项目统计；
2. 1080 × 1350 JPEG 纪念海报。

个人海报包含收件人姓名和项目冻结数据。渲染失败时只降级为 Markdown 或普通卡片，不阻断已经写入的站内通知，也不改写业务状态。图片通过企业微信长连接的三段上传协议取得 `media_id` 后再发送；不把大图作为命令文件内的裸 base64 直接塞进 `aibot_send_msg`。

### 2.5 企业微信项目群

群消息由 MEMBER 可见动态 `PROJECT_WRAPPED` 物化，不使用个人通知类型作为群来源，避免同一次封箱产生两条群消息。该动态归入现有 `project.member` 群通知类别：项目群关闭「项目与成员变化」时不推；个人单聊不受群开关影响。

群投递发送「叮——最后一盏灯灭了。」与同一张无收件人署名的海报。迁移给 `app.wecom_group_deliveries` 增加 `delivered_step_count`：文字成功而图片失败或进程重启时，只重试未完成段，不重复已送达文字。两段都成功后才把投递行标记为 `SENT`。

限速、临时错误、绑定失效和最终失败继续沿用 ADR-077 / ADR-090 的既有队列语义；一个项目一个群、一个群一个项目的绑定不变量不变。

### 2.6 海报渲染

- 模板版本固定为 1，桥接必须拒绝未知版本，不能把新字段猜成旧模板。
- 海报使用仓库内品牌标识与确定性布局，不依赖远程图片、模型生成或运行时随机数。
- 海报只使用随桥接资产分发的 Noto Sans SC Regular / Black（SIL Open Font License 1.1）；Windows 与 Linux 加载同一组字体文件，不再回退到微软雅黑、黑体或 Arial。`fonts-noto-cjk` 仅作为运行镜像的兜底，不参与日常渲染；许可文本随字体资产保存。
- 所有项目名、成员名与路径均来自快照并经过 XML 转义；海报是展示层，不参与权限判断。

## 3. 非目标

- 不追溯历史维护中项目，不提供管理员“补发封箱”入口。
- 不为海报增加公开分享链接、落地页、对象存储或附件生命周期管理。
- 不新增可视化编辑器、模板市场或按项目自定义主题。
- 不把封箱视为删除、只读或归档；维护中项目的既有读写规则不变。
- 不因为任务完成、记录发布等事件自动提前封箱。
- 不让项目群消息和个人单聊互相替代；两条通道继续并存。
- 不在本批引入 WebSocket、通用 Outbox 或新的后台任务框架。

## 4. 后果与验收

- 项目第一次完成交付时产生一次不可变纪念快照，并形成可回看的审计、项目动态与站内通知。
- 项目群和个人会话都能收到文字加海报；群开关、个人偏好和绑定状态继续分别生效。
- 封箱快照只增不改，后续成员离职、任务重开或记录修订不会改写历史海报。
- 路由总数保持 129，不新增 API；迁移文件共 55 条，最高序号为 0056。
- 定向验收覆盖：首次进入维护中写一项快照与 `PROJECT_WRAPPED` 动态、全部活跃成员收到 `project.wrapped` 通知、重复进入维护中不重复封箱、无完成任务或仍有未收尾任务不封箱、项目物理删除级联清理快照、桥接模板校验与海报 JPEG 渲染、群投递分段断点续传。测试明细见 [测试矩阵](../test-matrix.md)。
